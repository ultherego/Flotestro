3. Installation

An installation that does not exist yet, brought up in the order the parts depend on each other: the control plane, the first administrator and the group mappings, the backup pair before there is a fleet to lose, and only then the hosts. The short form of this chapter is the runbook docs/runbooks/install.md; this is the long one.

Before you start

  • PostgreSQL 16 or newer that this installation will own, reachable from the panel's host - or the quick-start profile, which brings one up beside it.
  • A container runtime: Docker Engine with the Compose plugin, or Podman. The panel and the relay are images and are deployed no other way; there is no container at all on the managed hosts.
  • DNS that resolves the names the panel will advertise, from the hosts and from the operator's browser. Those names enter the agent gateway's certificate, so they are the names the fleet really reaches - never a Compose service name. A laboratory needs none of it: an address serves where a name would, and the panel offers the ones it finds on its own machine.
  • Ports: 8080 for the panel and its API, published on every address of its host; 8443 and 8444 reached by the fleet directly. The TLS of the last two is end to end and must not be terminated by an HTTP proxy. An installation that puts a reverse proxy in front of the panel narrows 8080 back to the loopback with FLOTESTRO_API_PUBLISH.
  • A signed package repository the hosts can reach. The release publishes one; an isolated site runs the package-repository image of the air-gapped profile.

The server runs in a container; the hosts do not. The agent and its helper are native packages, because a host agent that has to see the real /proc, the real disks and the real systemd would be a --privileged container with nothing isolated about it.

The control plane from its image

There are four deployments and they are one compose.yaml, varied by a profile or by an overlay file. Nothing beyond the panel, its database and the one-shot services that prepare it starts unless it is named: a connected site does not quietly publish a package repository, and an installation that points at a database of its own takes the local one out with an overlay rather than leaving it running empty beside the real one.

DeploymentCommandFor
Quick startdocker compose up -dThe panel and a PostgreSQL of its own on one host, with nothing prepared. A laboratory, a demonstration, a small installation.
Production basicdocker compose -f compose.yaml -f compose.external-db.yaml up -dOne control plane against an external, backed-up PostgreSQL. The default for a company. The overlay takes the local database out and holds the DSN to a verified server.
Production relaydocker compose -f compose.relay.yaml up -d on each site hostThe same, plus one relay per site next to the agents it serves.
Air-gapped--profile airgap added to either of the first twoAny of the above, plus the package repository of the release on the network the managed hosts reach.

Which database an installation uses is chosen before it is initialised. Moving a live one to another database is a data migration, not a change of a variable.

The first start

The quick start needs nothing prepared. One file, one command, and the panel is up with a database of its own:

On the panel host

curl -fsSLO https://raw.githubusercontent.com/ultherego/Flotestro/main/docker/compose.yaml
docker compose up -d
docker compose cp control-plane:/var/lib/flotestro/bootstrap-token .

Under rootless Podman, fetch one more file and run it once per host before the up; without it the panel is down after the first reboot of the machine. Under the Docker daemon there is nothing to prepare:

curl -fsSLO https://raw.githubusercontent.com/ultherego/Flotestro/main/docker/host-setup.sh
chmod +x host-setup.sh
./host-setup.sh
podman-compose up -d

Then, from another machine:

  1. Open http://<the panel host's address>:8080. Port 8080 is published on every address of the host, so no domain, no certificate and no tunnel are involved.
  2. Sign in with the token in ./bootstrap-token.
  3. Confirm the address the agents dial, on the first-run screen. The panel offers the addresses it finds on that machine and adopts none of them by itself: it cannot tell which of them the hosts route to, and the wrong one enrols a fleet that drops out again.
  4. Install an agent on a separate host with the commands the Add host screen prints for it, and enrol it.

That is plain HTTP

The bootstrap token and every administrative request travel in clear on the network. It is the accepted price of a deployment with nothing to prepare, and it is a laboratory's price to pay; a company running a fleet from this panel puts TLS in front of it — a reverse proxy, a certificate, a domain — and narrows FLOTESTRO_API_PUBLISH to the loopback when it does. The fleet's own traffic is unaffected either way: the enrollment on 8444 and the agents' mTLS on 8443 terminate their own TLS against Flotestro's PKI and never pass through an HTTP proxy.

Every setting has a working default, so none of that needs .env at all. env.example lists every setting and names the three that matter, and an identity provider is not among them: a panel with no OIDC issuer and no FreeIPA signs its operators in with API tokens, which the first-run checklist counts as a choice rather than as an unfinished step.

Production basic, against a database somebody else runs. The overlay compose.external-db.yaml is what makes it that installation: it takes the local database out, sets FLOTESTRO_DATABASE_MODE=external and passes the DSN as a Compose secret. Write the DSN before the first start:

cat > .env <<'SETTINGS'
FLOTESTRO_VERSION=0.62.0
FLOTESTRO_GATEWAY_ID=cp-prod-01
FLOTESTRO_ADVERTISE=panel.example.org
FLOTESTRO_PUBLIC_URL=https://panel.example.org
SETTINGS

mkdir -p secrets && chmod 700 secrets
printf '%s' 'postgresql://flotestro:PASSWORD@db.example.org:5432/flotestro?sslmode=verify-full&target_session_attrs=read-write&application_name=flotestro-control-plane' > secrets/database-url
chmod 600 secrets/database-url

docker compose -f compose.yaml -f compose.external-db.yaml run --rm migrate
docker compose -f compose.yaml -f compose.external-db.yaml up -d
docker compose logs -f control-plane        # wait for "the database schema is current"
curl -fsS http://127.0.0.1:8080/readyz

/readyz and not /healthz: the latter answers while the process is alive, which it is when the database is unreachable and when the database has become a read-only standby.

In that order and not the other way. The schema is brought forward by a run of its own, and a panel that serves refuses a schema it does not match rather than reshape one somebody else owns. That is also what makes a second replica possible: an upgrade is one migration and then the replicas rolled, which cannot be true if every instance migrates at its own start.

external mode holds the DSN to sslmode=verify-full and target_session_attrs=read-write and refuses it otherwise, and a preflight asks the database what it is - a standby, its extensions, the rights of the login - before the panel settles on it. No refusal carries the DSN, because it holds the password. verify-full needs the issuing authority, and the image carries the public bundle alone: a database with an authority of its own is named with sslrootcert= and the file mounted, as the header of the overlay shows.

Separating the database roles is a further step and worth taking: the login the panel serves on then has no right to change the schema, and a second one migrates as the owner. db/roles.sql creates them, and the migration is pointed at its own DSN with FLOTESTRO_MIGRATION_DATABASE_URL_FILE. Without it the migration uses the serving login, which still keeps the migration out of the serving process but gives up the separation.

Nothing to prepare

  • The init service writes the DSN and the database password into a volume and gives each file to the account that reads it, inside the runtime. No chown, and no uid to get right.
  • Docker and rootless Podman behave the same, because no host account owns the files any more.
  • ./secrets is mounted :ro,z, so a host with SELinux relabels it by itself instead of failing with a plain “permission denied”.
  • One difference remains: podman-compose has no cp, so the bootstrap token is fetched with podman cp flotestro_control-plane_1:/var/lib/flotestro/bootstrap-token . instead.
  • A reboot is the other, and under Podman it needs two settings and no more. The Docker daemon starts with the machine and brings the containers back with it; rootless Podman has no daemon that would. Lingering keeps the containers running after the last logout, and a unit shipped with Podman replays the restart policies at boot. Both are set once, as the account that runs the deployment, by ./host-setup.sh, which changes only what is not already set and says what it found. What it does is these two commands, so you can see it without running it: loginctl enable-linger $USER and systemctl --user enable podman-restart.service. ./host-setup.sh --check changes nothing and answers whether this host brings the deployment back after a reboot, exiting non-zero when something is missing; it also warns if a compose file beside it says restart: unless-stopped. Under the Docker daemon it says there is nothing to do. That is the whole of it because the compose files say restart: always, not restart: unless-stopped: the unit runs podman start --all --filter restart-policy=always, so a deployment that said unless-stopped would be skipped, and the unit would report success and start nothing. The Docker daemon honours always at its own start too, so both engines behave the same way. A host that has to come up with the panel deliberately down is taken down with podman-compose down, not by leaving a stopped container behind: a container that is merely stopped is started again at the next boot, which is what the policy says and what the fleet needs. The relay's compose file says the same.

Secrets are files, never variables

Every secret setting has a _FILE form that names a path; the value form and the _FILE form must not both be set, and an empty file, a symlink, a directory or a file readable by anyone else is refused. An environment variable is visible in docker inspect and in the host's process list, which is why the DSN travels as a path.

Pin a digest, and check what you are about to run

The release prints the digest of each image and attaches a ready compose.pins.yaml to its run. A tag is what a human reads; a digest is what is deployed, and a tag can be rewritten by whoever publishes it.

docker compose -f compose.yaml -f compose.pins.yaml up -d

The signature is keyless: it was made against the identity of the workflow and recorded in the public transparency log, so there is no key to steal and none to distribute. Check the identity, not merely that a signature exists:

cosign verify \
  --certificate-identity-regexp '^https://github\.com/ultherego/Flotestro/\.github/workflows/images\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/ultherego/flotestro-control-plane:0.62.0@sha256:...

The bill of materials and the provenance are read the same way with cosign verify-attestation --type cyclonedx and docker buildx imagetools inspect. A workflow run that received no OIDC identity publishes the image unsigned and says so in its log; a cosign verify against such an image fails, which is the correct answer and not a malfunction.

The first administrator, and the mappings without which nobody can sign in

An installation with no identities writes a bootstrap token into its state directory. It is the only way in before the identity provider is connected, and it is meant to be spent and deleted.

docker compose cp control-plane:/var/lib/flotestro/bootstrap-token ./bootstrap-token

Then, in this order:

  1. Sign in with the token.
  2. Connect the identity provider: FLOTESTRO_OIDC_ISSUER, FLOTESTRO_OIDC_CLIENT_ID (default flotestro-panel) and FLOTESTRO_OIDC_CLIENT_SECRET. An empty issuer disables browser login altogether and the panel then works on API tokens alone. FLOTESTRO_PUBLIC_URL decides the redirect and the Secure flag of the cookies, so it has to be the address the browser really uses.
  3. Map at least one group to a role. A group grants nothing by itself. With no mapping, whoever signs in through the provider gets no permission at all - that is the single most common reason a fresh installation looks broken.
  4. Sign in through the provider and confirm you have what the mapping granted.
  5. Revoke the bootstrap token and delete ./bootstrap-token. The control plane warns at every start while it is still valid.

Steps 2 to 4 belong to an installation that has an identity provider. One that stays on API tokens skips them and is not behind: the checklist marks both the provider and the group mapping optional and counts neither. What it does not skip is the handover — issue an API token of your own with platform_admin, sign in with it, and only then revoke the bootstrap one.

A mapping is a group of an issuer, a role and a scope. The panel writes them on the access screen; the request behind the button is:

POST /api/v1/group-mappings
{
  "issuer":      "https://sso.example.org/realms/flotestro",
  "group_name":  "linux-platform",
  "role":        "platform_admin",
  "site":        "*",
  "environment": "*",
  "reason":      "the platform team administers the installation"
}

The permission needed to write one is principal.manage in the whole fleet; an unknown role is refused with unknown_role. Leaving the issuer out fills in the configured one. The roles are viewer, auditor, operator, approver, identity_admin and platform_admin; site and environment take * for the whole fleet or an exact value to scope the grant.

The checklist the panel keeps

GET /api/v1/setup is what the setup screen and the dashboard card read. It answers with the steps in the order they are taken, how many are done, which is next, and whether the bootstrap token still opens the panel:

StepDone when
identity_providerThe issuer answers and names its signing keys. An installation that named no issuer is optional and is not counted: it signs its operators in with API tokens. One that named an issuer it cannot reach is warning and says what the issuer answered, because that is a fault and not a choice.
group_mappingAt least one group decides a role at login. With no identity provider there is no login token to map, so the step is optional; with one configured and no mapping it stays undone, because the panel then signs people in and grants them nothing.
bootstrap_tokenThe token is revoked or expired - that is, it no longer works. It stays undone while it is the only fleet administrator, and what to do about it follows the installation: create the first group mapping where there is a provider, issue an API token of your own where there is none.
directoryOptional: the FreeIPA connector is configured. A connector whose keytab cannot be read, or that has stopped answering, is reported as the fault it is.
hostsAt least one host is enrolled and not retired.
relayOptional: needed only for a site whose hosts cannot reach the panel directly.
policyAt least one policy declares what is to be true on the hosts; without one the panel reports the hosts as they are and judges nothing.
alert_rule, notification_channelSomething evaluates the samples, and somewhere to send what it finds. Both are optional steps: they do not hold the checklist back.
fleet_caWarns 30 days before the CA's end, because a rotation needs every agent to renew once under the new CA and agent certificates live thirty days.

Back up before the fleet exists

The database and the state directory are one pair. The database holds the hosts, the tasks, the campaigns, the audit trail, the monitoring and the encrypted secrets; the state directory holds the keys those ciphertexts open with and the CA the fleet's certificates were issued by. Take the pair now, while the CA is minutes old, and prove the restore before the fleet depends on it.

That is the pair while the keys are files. An installation that has moved its keys into the database has a different one: the dump and the key encryption key and the installation identifier, and the state directory then holds nothing that cannot be made again (see the key encryption key).

Once, before the first backup

# ./backups is made and given to the right account by the init service.
docker compose --profile tools run --rm admin-tools backup

The backup itself, with the control plane stopped - or at least with the CA and key rotation held

docker compose --profile tools run --rm admin-tools backup

It writes ./backups/<backup-id>/ and nothing outside it:

FileWhat it is
database.dumppg_dump --format=custom, without owners and without privileges: the restore is done by whoever owns the empty database it goes into.
state.tar.zstThe state directory with numeric owners and the original modes - the directory is 0700 and the keys in it 0600.
manifest.jsonWhat ties the halves together: the backup identifier, the moment, the version and commit of the image, the installation identifier, the active key and issuer identifiers, the kek_id of the key encryption key the rows are sealed with (a db-sealed installation only), the digests of both files, and the image digest when the deployment pins one. No DSN, no password, no secret value.
SHA256SUMSThe digests of the two archives, checked before every restore.

A pair can be checked without restoring anything, and a restore is a profile of its own because it is the one operation that mounts the state writable:

docker compose --profile tools   run --rm admin-tools   verify  20260919T101500Z
docker compose --profile restore run --rm admin-restore restore 20260919T101500Z

The restore refuses to start unless the checksums match, the state volume is empty and the target database has no tables in its public schema. It puts an installation back where there is none; it never writes over the identity of one that is still there.

The backup does not take the key encryption key

admin-tools backup takes the database and the state directory. It does not take the key encryption key, deliberately: that key is kept apart, by different people. The manifest records only its kek_id, so that a restore can tell whether the key in hand is the one that opens the dump; the key itself is not in the backup and must not be.

The archives hold secrets

The manifest does not, but database.dump and state.tar.zst do. The backup belongs on encrypted storage, away from the host it was taken from, and it is worth restoring it into an isolated environment now and again to find out whether it actually works.

The key encryption key

The private keys of an installation - the keys the secret store seals its values with, the private key of the fleet CA and of a CA prepared to take over, the key that signs the root helper's capabilities - can live as rows of the database instead of files in the state directory. Each row is sealed with a key encryption key that the deployment mounts as a secret. The rows travel with the database, so every replica reads the same keys; the key does not, so a copy of the dump alone opens nothing.

Nothing here happens by itself. The panel does not migrate at start, does not rewrap on a schedule and never removes a key file. The full procedure is the runbook docs/runbooks/key-encryption-key.md; this is what to know before you start it.

The key itself

Exactly one format is accepted: 64 hexadecimal characters, which is 32 bytes, with at most one trailing newline. The wrong length, a character outside hexadecimal, a second line or an empty file is refused rather than repaired, because a key that was quietly tidied up is a key nobody can reproduce.

umask 077
openssl rand -hex 32 > flotestro-kek

The file is read without following a link and judged on the descriptor that was opened. It must be a regular file, not a symlink, owned by root or by the panel's own account, mode 0400, and neither readable nor writable by the group or by anybody else. The panel looks for it at /run/secrets/flotestro-kek; another path is named with -kek-file or FLOTESTRO_KEK_FILE. Only the path is configured: there is no flag and no environment variable that carries the key itself.

In the Compose deployment you put the key in ./secrets/kek and init copies it to /run/flotestro/kek, where FLOTESTRO_KEK_FILE points, with the mode and owner the panel insists on. ./secrets/ is what the deployment holds: init copies it over the volume at every start of the control plane, because starting a container starts what it depends on. A key changed in ./secrets/ therefore takes effect, and one changed in the volume does not. A key added to a deployment that already runs reaches the panel once init has run again, and under Podman that takes two steps, not podman restart: the control plane depends on init and migrate, which have run and exited, and Podman refuses with “some dependencies of container ... are not started”.

podman stop flotestro_control-plane_1
podman start flotestro_control-plane_1

A backup is three things, kept apart

A backup that can be restored is the database dump and the key encryption key and the installation identifier. Any two of the three are not a backup. The key belongs in a different backup from the dump, kept by different people.

The four commands

They are subcommands of flotestro-control-plane crypto, run from a host that reaches the fleet database (the image's binary, or the admin-tools container), after a recent pg_dump. Every one of them takes --dry-run, which prints what the run will print and changes nothing, and requires --backup-to, the directory the state before the change is written to; a command refuses to overwrite a file it finds there, and the directory must not be inside the state directory, because crypto forget-files copies the key files there before removing them.

CommandWhat it does
crypto import-stateMoves the keys found in the state directory into the database. Every key is wrapped and read back before anything is written, and all of them are written with the installation record in a single transaction: one key that cannot be read back stops the migration. The files are not removed; until you say otherwise they are the way back. Then restart the control plane with the key in place (stop, then start, as above).
crypto revert-stateMoves the keys back into files. The files are written first and the rows dropped only once they are there, so an interrupted revert leaves the keys in the database rather than nowhere.
crypto rewrap-kek --new-kek-file pathRotates the key encryption key. The keys themselves do not change - only the wrapping - so it can be done with the panel running. The new key goes in ./secrets/kek-next, init puts it at /run/flotestro/kek-next at the next start of the control plane, and the command is crypto rewrap-kek -new-kek-file /run/flotestro/kek-next. Every row and the record move together. The panel uses whichever of the two keys the installation record names, so a replica restarted at any point in the rotation comes back; there is no window. Then make the new key the deployment's key (./secrets/kek-next becomes ./secrets/kek) and restart every replica. Once kek-next is gone, a replica that never saw the new key refuses to start with kek_mismatch, so keep the file until every replica has been restarted.
crypto forget-files -expect-revision revision -confirm-installation installation-idRemoves the key files and so closes the way back. It refuses on the first of six checks that fails (the migration is finished and with this key, every key opens from the database and matches its file, the marker in the state directory names this installation, the crypto state still stands at the revision you pass, you said the installation identifier back, and the warning about what stops working is printed first). The revision and the identifier are in the crypto block of GET /api/v1/status.

The rotation's backup holds the rows as they were; they open with the old key and with no other, so keep that key until every replica runs on the new one. To see where an installation stands, read the crypto block of GET /api/v1/status: provider is local-sealed while the keys are files and db-sealed once they are rows, and then the block also carries kek_id.

forget-files is not a secure erase

The files are copied into the backup directory before they go. What the command then does is remove and unlink them and synchronise the directories. On an SSD, on a copy-on-write filesystem or on network storage that is not a guaranteed physical erasure of the bytes, and nothing here claims otherwise. If the material must be provably gone, that is a property of the storage, not of this command. After it, a panel from before the keys moved into the database will not start against this installation without a backup of those files.

Refusals

A start with the keys in the database refuses, and changes nothing, in five ways. A wrong key is not a rollback situation: mount the right one.

CodeWhen
kek_file_missingThere is no file at the path the deployment names.
kek_file_unsafeThe file is a link, not a regular file, owned by somebody else, or readable or writable by the group or by anybody else.
kek_file_malformedThe content is not 64 hexadecimal characters with at most one trailing newline.
kek_mismatchNone of the mounted keys is the one the installation records: a key of another installation, or the key from before a rotation whose new key is no longer mounted. A rotation under way does not end here.
kek_rotatedA replica asked to write a key sealed with the key it loaded at its start, and the installation has moved to another one since - a rewrap that finished while it was running. Nothing was written: that row would have been the one key of the installation nobody could open. Restart the replica onto the key the record now names.
wrapped_key_installation_mismatchA row belongs to another installation. A key encryption key is named after the key material, so two deployments that mount the same key name it the same; the installation on the row is what tells them apart. Take the row out of this database.
wrapped_key_unreadableA row does not open under the key the deployment holds although it says it was wrapped with it: it was changed, or it is in a form this panel does not read.

The hosts

The panel generates the exact commands per host and per family under Add host: the repository, the package, the fleet CA with its fingerprint to compare, the enrollment and the start. Use those - they carry this installation's own addresses, its one-time token and the CA the fleet really uses. The shapes below are here so that an operator knows what is being run.

StepWhat it does
repositoryAdds the signed repository and its key to apt, dnf or pacman.
packageInstalls flotestro-agent, which brings the helper with it.
CAWrites the fleet CA where the agent reads it, and prints its fingerprint to compare.
enrollSpends the one-time token and takes the host's own certificate.
startsystemctl enable --now flotestro-agent.

From the signed repository

sudo install -d -m 0755 /etc/apt/keyrings
curl -fsS https://ultherego.github.io/Flotestro/packages/flotestro-repo.asc | sudo tee /etc/apt/keyrings/flotestro.asc >/dev/null
echo 'deb [signed-by=/etc/apt/keyrings/flotestro.asc] https://ultherego.github.io/Flotestro/packages/deb stable main' | sudo tee /etc/apt/sources.list.d/flotestro.list >/dev/null
sudo apt update && sudo apt install flotestro-agent

Every index is signed by the release key, and there is no version in any of those lines: apt update is how a host learns a newer version exists and apt upgrade is what moves it. A pre-release goes to a testing channel that a host asking for stable never reads. dnf and pacman read the same tree under rpm/stable and arch/stable. One pacman database serves one architecture, so arch/<channel> is the x86_64 repository and any other architecture stands in arch/<channel>/<architecture> for a host configured by hand.

Without a route out

The file name carries the version, so there is no latest URL to quote; gh resolves the newest stable release itself, and pre-releases are not in it.

curl -fsS https://ultherego.github.io/Flotestro/packages/flotestro-repo.asc | gpg --import
gh release download --repo ultherego/Flotestro --pattern 'flotestro-agent_*_amd64.deb' --pattern 'SHA256SUMS*'
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
sudo apt install ./flotestro-agent_*_amd64.deb

gh attestation verify flotestro-agent_1.2.3_amd64.deb --repo ultherego/Flotestro

Enrollment

sudo tee /var/lib/flotestro-agent/ca.pem >/dev/null   # the fleet CA; compare the fingerprint with the panel
sudo sed -i -e 's|^  enrollment_url: .*|  enrollment_url: "https://panel.example.org:8444"|' \
            -e 's|^  gateway_urls: .*|  gateway_urls: ["https://panel.example.org:8443"]|' /etc/flotestro/agent.yaml
echo "$TOKEN" | sudo -u flotestro-agent flotestro-agentctl enroll
sudo systemctl enable --now flotestro-agent
flotestro-agentctl diagnose                            # explains a host that does not show up

The token is one-time and short-lived

Pass it by file or on standard input, never in the environment: sudo -u flotestro-agent flotestro-agentctl enroll --token-file /run/token, and delete the file afterwards. The daemon itself never enrolls - FLOTESTRO_ENROLLMENT_TOKEN in its environment is ignored and reported at every start until it is removed.

A host that already holds an identity keeps it: a package upgrade does not re-enroll, and an enrollment onto a host that carried a previous installation is refused with machine_already_enrolled - a new fleet CA does not recognise certificates the previous one issued. Remove the identity explicitly first; the sanitisation is in the golden-image runbook.

A machine that is a copy of another answers duplicate_machine_id at the certificate step or machine_id_mismatch at the token step: the host row is keyed by /etc/machine-id, and two machines sharing one are one host as far as the panel is concerned.

For a whole inventory at once there is an Ansible role in ansible. For machines started from an image, the agent package installs flotestro-enroll.service, which runs on the first boot only - when identity/current/agent.pem does not exist - so every clone enrolls as a host of its own.

A site behind a relay

Create relay.yaml and relay-ca.pem next to compose.relay.yaml before the first start: a bind mount whose source does not exist becomes a directory. Then register the relay with a one-time token from the panel and start it; the token file is deleted afterwards.

docker compose -f compose.relay.yaml --profile enroll run --rm relay-enroll
docker compose -f compose.relay.yaml up -d

relay.yaml

schema_version: 1
relay:
  name: "relay-waw-01"
  site: "warsaw"
  listen: "0.0.0.0:8453"
  advertised_names:
    - "relay-waw-01.example.com"
  state_dir: "/var/lib/flotestro-relay"
  buffer_max_bytes: 268435456
upstream:
  enrollment_url: "https://enroll.flotestro.example.com"
  gateway_urls:
    - "https://gateway-a.flotestro.example.com:8443"
    - "https://gateway-b.flotestro.example.com:8443"
  bootstrap_ca_file: "/etc/flotestro/bootstrap-ca.pem"

The relay is configured by that file and by nothing else. It lives beside compose.relay.yaml on the site host and is bind-mounted read-only at /etc/flotestro/relay.yaml; docker compose -f compose.relay.yaml run --rm relay config show prints what it resolves to. Its site is an expectation - the scope a relay really has is the one its enrollment token granted. No relay may advertise a name that is in FLOTESTRO_ADVERTISE. Its spool is on disk and survives a restart, so give the filesystem room: spool.max_bytes is 1 GiB by default and nothing is appended below spool.min_free_bytes, 256 MiB.

The air-gapped profile

An isolated site receives the release on media and nothing else. Four images cross the gap: the control plane, the package repository (the fleet installs its agents from it and from nowhere else), the admin tools (a site that cannot pull an image cannot improvise one on the day it has to restore) and, where the site has one, the relay. PostgreSQL is the site's own, from whatever channel it already trusts for its databases.

On the connected side

Verify the identity of each image first, then take it: a signature checked after the crossing would be a signature checked against a transparency log the site cannot reach.

# The three images the publishing workflow builds and signs.
for name in control-plane admin-tools relay; do
  reference="ghcr.io/ultherego/flotestro-$name:$version"
  cosign verify \
    --certificate-identity-regexp '^https://github\.com/ultherego/Flotestro/\.github/workflows/images\.yml@refs/tags/v' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com "$reference" \
    || { echo "$reference does not verify; it was not copied" >&2; break; }
  docker pull "$reference"
  docker save -o "flotestro-$name-$version.tar" "$reference"
done

# The repository of packages is built by the release workflow, so its signature carries that workflow's identity.
for name in package-repository; do
  reference="ghcr.io/ultherego/flotestro-$name:$version"
  cosign verify \
    --certificate-identity-regexp '^https://github\.com/ultherego/Flotestro/\.github/workflows/release\.yml@refs/tags/v' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com "$reference" \
    || { echo "$reference does not verify; it was not copied" >&2; break; }
  docker pull "$reference"
  docker save -o "flotestro-$name-$version.tar" "$reference"
done

Then write down what the isolated side is to check, and sign it with the same GPG key the packages are signed with - that key is the one trust anchor the site already has, and the only one that survives a gap. Record the image id, not the registry digest: docker save writes an archive of its own and docker load gives the image a new manifest, so the sha256: the release printed does not survive the crossing, and compose.pins.yaml is not usable there. A site with a local registry has the other option - skopeo copy keeps the manifest and then the digest pin works as everywhere else.

On the isolated side

gpg --import flotestro-repo.asc
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum --check --strict SHA256SUMS
for archive in flotestro-*.tar; do docker load -i "$archive"; done
# then compare each loaded image id against the signed IMAGE-IDS file

The images keep their ghcr.io/ultherego/... names although the site cannot reach that registry. That is deliberate: docker load restores an image under exactly the name it was saved with, the Compose files name it the same way, and an image renamed at the gap is one nobody can match against what was signed. Nothing pulls, because every reference already resolves locally.

Pointing the panel at the local repository

cat >> .env <<'SETTINGS'
FLOTESTRO_PACKAGE_REPOSITORY_URL=http://panel.site.example.org:8090
FLOTESTRO_VULN_NVD_URL=
SETTINGS

docker compose --profile airgap up -d

The panel does not serve the repository and does not proxy it: it composes the "Add host" commands from one address and the hosts fetch from that address themselves, so it is the address the hosts reach - never a Compose service name. Left empty, it leaves a placeholder in those commands and the Add host screen says so in a warning; it is not a setting the panel guesses. NVD is read from a live API and has no offline form, so an isolated site clears it rather than letting a timer fail every six hours.

Plain HTTP is not a weakness there. What a package manager trusts is the signature over the index and the key it imported once, and a package is verified on an isolated site exactly as it is anywhere else. A site that wants TLS puts the same edge in front of port 8090 as in front of the panel.

What an isolated site loses, and what it does not

Everything the fleet is managed with keeps working: inventory, tasks, campaigns, monitoring and its rules, the audit trail, backups, agent upgrades from the local repository. The vulnerability assessment is local too - the hosts report their package lists, the panel compares versions with dpkg and rpm rules of its own, and the feed snapshots live in the database. What it loses is fresh feed data: the status block vulnerability_feeds answers unknown while no feed has ever been read and failed once a snapshot is older than FLOTESTRO_VULN_MAX_SNAPSHOT_AGE (six hours by default). Per host, feed_stale still produces findings while feed_missing produces none at all - and the panel says in as many words that zero findings there means nothing could be checked.

Verification

  • GET /api/v1/status: the schema is current, the database answers, and the instance claims its gateway identity.
  • GET /api/v1/hosts: every enrolled host is online and reports its distribution and its agent version.
  • One operation end to end on one host - a read is enough - reaches a terminal state with a result, not a refusal.
  • The panel shows no bootstrap token warning, and ./bootstrap-token is deleted.
  • The backup pair exists and has been restored once, somewhere that is not production.

Rollback, upgrades and removal

Nothing here is irreversible until hosts are enrolled. Before that, docker compose down -v and an empty database put the machine back. After that, a host is removed by sanitising it - the identity, the task state and the firewall registry - and the panel decommissions its record.

An upgrade is three decisions in one order, and the order is not a matter of taste, because the control plane refuses to serve a schema it does not match in either direction:

  1. Take the pair, with the new images pulled but nothing started from them. A backup taken after the migration is a backup of the version you are trying to leave.
  2. Ask what the new version would do: docker compose --profile check run --rm schema-check. Exit 0 means no migration and the upgrade is a restart; exit 1 with schema_behind means it carries migrations and names how many. Any other answer stops the upgrade. The service is schema-check and not the control plane with that word after it: run starts what the named service depends on, and the control plane depends on migrate - asked that way the question would perform the migration it is about.
  3. Migrate once, as its own job, with the migrator's credentials: docker compose run --rm control-plane migrate. Two migrators do not race - the second waits on the advisory lock and says so. Run schema-check again; it must now exit 0.
  4. Roll the replicas one at a time, watching the fleet reconnect between them. The agents are upgraded afterwards and separately, by the panel itself.

Going back has one asymmetry: a version can be gone back to, a schema cannot. If the new version applied no migration, put the previous image back and start it. If it migrated, the old control plane refuses to start with schema_ahead and is right to - going back then means restoring the pair from step 1 and losing everything recorded since. Never delete rows from schema_migrations to make the two agree; the tables are still the new ones and the panel would write into a shape it misreads.

Removing an installation for good is deliberate and in this order: decommission the hosts while the panel still runs, so each one stops trusting the centre and revokes its own certificate; take a last backup pair if the audit trail has to outlive the panel; docker compose down --volumes, which takes the state volume with it; and then the database, if it is one this installation owns. What remains on a managed host is the agent package itself, which apt purge, dnf remove or pacman -Rns removes together with its identity files.

down keeps the volumes on purpose

A plain docker compose down stops the containers and leaves the state and the database where they are, because an operator stopping a panel for an hour must not lose the fleet's certificate authority by typing the usual command. Only --volumes takes the state.
