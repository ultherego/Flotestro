3. Installation

An installation that does not exist yet, brought up in the order the parts depend on each other: the control plane, the first administrator and the group mappings, the backup pair before there is a fleet to lose, and only then the hosts. The short form of this chapter is the runbook docs/runbooks/install.md; this is the long one.

Before you start

  • PostgreSQL 16 or newer that this installation will own, reachable from the panel's host - or the quick-start profile, which brings one up beside it.
  • A container runtime: Docker Engine with the Compose plugin, or Podman. There is also a package path for the control plane, and no container at all on the managed hosts.
  • DNS that resolves the names the panel will advertise, from the hosts and from the operator's browser. Those names enter the agent gateway's certificate, so they are the names the fleet really reaches - never a Compose service name.
  • Ports: 8080 for the panel behind a reverse proxy, 8443 and 8444 reached by the fleet directly. The TLS of the last two is end to end and must not be terminated by an HTTP proxy.
  • A signed package repository the hosts can reach. The release publishes one; an isolated site runs the package-repository image of the air-gapped profile.

The server runs in a container; the hosts do not. The agent and its helper are native packages, because a host agent that has to see the real /proc, the real disks and the real systemd would be a --privileged container with nothing isolated about it.

The control plane from its image

There are four deployments, and they are profiles of one compose.yaml. The control plane is the only service without a profile, so nothing else ever starts unless it is named: an installation pointed at an external database cannot quietly start a second, empty one beside it, and a connected site does not quietly publish a package repository.

DeploymentCommandFor
Quick startdocker compose --profile quickstart up -dThe panel and a PostgreSQL of its own on one host. A laboratory, a demonstration, a small installation.
Production basicdocker compose up -dOne control plane against an external, backed-up PostgreSQL. The default for a company.
Production relaydocker compose -f compose.relay.yaml up -d on each site hostThe same, plus one relay per site next to the agents it serves.
Air-gappeddocker compose --profile airgap up -dAny of the three, plus the package repository of the release on the network the managed hosts reach.

The first start

The quick start needs nothing prepared. One file, one command, and the panel is up with a database of its own:

On the panel host

curl -fsSLO https://raw.githubusercontent.com/ultherego/Flotestro/main/docker/compose.yaml
docker compose --profile quickstart up -d
docker compose cp control-plane:/var/lib/flotestro/bootstrap-token .

Every setting has a working default, so the panel answers on http://localhost:8080 straight away. To serve hosts on other machines, put the address they reach it at in .env beside the file — env.example lists every setting and names the three that matter.

Production basic, against a database somebody else runs. Leave the profile out and write the DSN before the first start; the init service reads it and hands the copy to the account the panel runs as, so no ownership is yours to get right:

cat > .env <<'SETTINGS'
FLOTESTRO_VERSION=0.60.1
FLOTESTRO_GATEWAY_ID=cp-prod-01
FLOTESTRO_ADVERTISE=panel.example.org
FLOTESTRO_PUBLIC_URL=https://panel.example.org
SETTINGS

mkdir -p secrets && chmod 700 secrets
printf '%s' 'postgresql://flotestro:PASSWORD@db.example.org:5432/flotestro?sslmode=verify-full&application_name=flotestro-control-plane' > secrets/database-url
chmod 600 secrets/database-url

docker compose up -d
docker compose logs -f control-plane        # wait for "the database schema is current"
curl -fsS http://127.0.0.1:8080/healthz

A DSN found in secrets/database-url always wins over anything generated earlier, so that is also how an installation moves off the quick-start database and how its password is changed. sslmode=disable is acceptable only for the quick start, on one host with an internal network. An external database requires verify-full.

Nothing to prepare

  • The init service writes the DSN and the database password into a volume and gives each file to the account that reads it, inside the runtime. No chown, and no uid to get right.
  • Docker and rootless Podman behave the same, because no host account owns the files any more.
  • ./secrets is mounted :ro,z, so a host with SELinux relabels it by itself instead of failing with a plain “permission denied”.

Secrets are files, never variables

Every secret setting has a _FILE form that names a path; the value form and the _FILE form must not both be set, and an empty file, a symlink, a directory or a file readable by anyone else is refused. An environment variable is visible in docker inspect and in the host's process list, which is why the DSN travels as a path.

SecretVariableMount
Database DSNFLOTESTRO_DATABASE_URL_FILE/run/secrets/database_url
OIDC client secretFLOTESTRO_OIDC_CLIENT_SECRET_FILE/run/secrets/oidc_client_secret
Webhook HMAC keyFLOTESTRO_WEBHOOK_SECRET_FILE/run/secrets/webhook_secret
NVD API keyFLOTESTRO_VULN_NVD_KEY_FILE/run/secrets/nvd_key
FreeIPA keytabFLOTESTRO_IPA_KEYTAB (already a path)/run/secrets/ipa.keytab
PostgreSQL password (quick start)POSTGRES_PASSWORD_FILE/run/secrets/postgres_password

Pin a digest, and check what you are about to run

The release prints the digest of each image and attaches a ready compose.pins.yaml to its run. A tag is what a human reads; a digest is what is deployed, and a tag can be rewritten by whoever publishes it.

docker compose -f compose.yaml -f compose.pins.yaml up -d

The signature is keyless: it was made against the identity of the workflow and recorded in the public transparency log, so there is no key to steal and none to distribute. Check the identity, not merely that a signature exists:

cosign verify \
  --certificate-identity-regexp '^https://github\.com/ultherego/Flotestro/\.github/workflows/images\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/ultherego/flotestro-control-plane:0.60.0@sha256:...

The bill of materials and the provenance are read the same way with cosign verify-attestation --type cyclonedx and docker buildx imagetools inspect. A workflow run that received no OIDC identity publishes the image unsigned and says so in its log; a cosign verify against such an image fails, which is the correct answer and not a malfunction.

… or the control plane from packages

The release also builds flotestro-control-plane as a .deb and an .rpm (pacman gets the agent and the relay only). The package brings the panel, the systemd unit, the configuration file and flotestro-auditverify, which stands next to the panel so that an export of the audit trail can be checked where the trail was written.

PathWhat it is
/usr/bin/flotestro-control-planeThe binary.
/usr/bin/flotestro-auditverifyThe offline verifier of an audit export.
/lib/systemd/system/flotestro-control-plane.serviceThe unit.
/etc/flotestro/control-plane.envEvery setting, commented. A configuration file: a package update does not overwrite it. Owned root:flotestro, mode 0640, because it holds the database credentials.
/var/lib/flotestroThe state directory, mode 0700, owned by the service account.
/usr/share/flotestro/webThe built panel; the unit points FLOTESTRO_WEB_ROOT at it.

The package makes a system account flotestro and enables the unit. It does not start it while the shipped DSN still says change-me: a panel without a database has nowhere to keep the fleet state, and a restart loop would only litter the journal. The installation ends with the two lines that finish it - set FLOTESTRO_DATABASE_URL, then systemctl start flotestro-control-plane.service.

Three settings in that file have to be changed before the panel is of any use: FLOTESTRO_DATABASE_URL, FLOTESTRO_ADVERTISE (empty by default, and the certificate issued without it covers 127.0.0.1 alone - an agent elsewhere rejects the connection) and FLOTESTRO_PUBLIC_URL.

The package's defaults are not all the binary's

The shipped control-plane.env sets FLOTESTRO_METRICS_RETENTION_RAW=48h and FLOTESTRO_METRICS_RETENTION_ROLLUP=720h, which are shorter than the binary's own defaults of 168h and 2160h. What the file sets is what the installation runs on. From the moment an operator stores a monitoring retention in the panel, the stored value decides and the file is only what a cleared field falls back to.

The first administrator, and the mappings without which nobody can sign in

An installation with no identities writes a bootstrap token into its state directory. It is the only way in before the identity provider is connected, and it is meant to be spent and deleted.

docker compose cp control-plane:/var/lib/flotestro/bootstrap-token ./bootstrap-token

Then, in this order:

  1. Sign in with the token.
  2. Connect the identity provider: FLOTESTRO_OIDC_ISSUER, FLOTESTRO_OIDC_CLIENT_ID (default flotestro-panel) and FLOTESTRO_OIDC_CLIENT_SECRET. An empty issuer disables browser login altogether and the panel then works on API tokens alone. FLOTESTRO_PUBLIC_URL decides the redirect and the Secure flag of the cookies, so it has to be the address the browser really uses.
  3. Map at least one group to a role. A group grants nothing by itself. With no mapping, whoever signs in through the provider gets no permission at all - that is the single most common reason a fresh installation looks broken.
  4. Sign in through the provider and confirm you have what the mapping granted.
  5. Revoke the bootstrap token and delete ./bootstrap-token. The control plane warns at every start while it is still valid.

A mapping is a group of an issuer, a role and a scope. The panel writes them on the access screen; the request behind the button is:

POST /api/v1/group-mappings
{
  "issuer":      "https://sso.example.org/realms/flotestro",
  "group_name":  "linux-platform",
  "role":        "platform_admin",
  "site":        "*",
  "environment": "*",
  "reason":      "the platform team administers the installation"
}

The permission needed to write one is principal.manage in the whole fleet; an unknown role is refused with unknown_role. Leaving the issuer out fills in the configured one. The roles are viewer, auditor, operator, approver, identity_admin and platform_admin; site and environment take * for the whole fleet or an exact value to scope the grant.

The checklist the panel keeps

GET /api/v1/setup is what the setup screen and the dashboard card read. It answers with the steps in the order they are taken, how many are done, which is next, and whether the bootstrap token still opens the panel:

StepDone when
identity_providerThe issuer answers and names its signing keys.
group_mappingAt least one group decides a role at login.
bootstrap_tokenThe token is revoked or expired - that is, it no longer works.
directoryOptional: the FreeIPA connector is configured.
hostsAt least one host is enrolled and not retired.
relayOptional: needed only for a site whose hosts cannot reach the panel directly.
policyAt least one policy declares what is to be true on the hosts; without one the panel reports the hosts as they are and judges nothing.
alert_rule, notification_channelSomething evaluates the samples, and somewhere to send what it finds. Both are optional steps: they do not hold the checklist back.
fleet_caWarns 30 days before the CA's end, because a rotation needs every agent to renew once under the new CA and agent certificates live thirty days.

Back up before the fleet exists

The database and the state directory are one pair. The database holds the hosts, the tasks, the campaigns, the audit trail, the monitoring and the encrypted secrets; the state directory holds the keys those ciphertexts open with and the CA the fleet's certificates were issued by. Take the pair now, while the CA is minutes old, and prove the restore before the fleet depends on it.

Once, before the first backup

# ./backups is made and given to the right account by the init service.
docker compose --profile tools run --rm admin-tools backup

The backup itself, with the control plane stopped - or at least with the CA and key rotation held

docker compose --profile tools run --rm admin-tools backup

It writes ./backups/<backup-id>/ and nothing outside it:

FileWhat it is
database.dumppg_dump --format=custom, without owners and without privileges: the restore is done by whoever owns the empty database it goes into.
state.tar.zstThe state directory with numeric owners and the original modes - the directory is 0700 and the keys in it 0600.
manifest.jsonWhat ties the halves together: the backup identifier, the moment, the version and commit of the image, the installation identifier, the active key and issuer identifiers, the digests of both files, and the image digest when the deployment pins one. No DSN, no password, no secret value.
SHA256SUMSThe digests of the two archives, checked before every restore.

A pair can be checked without restoring anything, and a restore is a profile of its own because it is the one operation that mounts the state writable:

docker compose --profile tools   run --rm admin-tools   verify  20260919T101500Z
docker compose --profile restore run --rm admin-restore restore 20260919T101500Z

The restore refuses to start unless the checksums match, the state volume is empty and the target database has no tables in its public schema. It puts an installation back where there is none; it never writes over the identity of one that is still there.

The archives hold secrets

The manifest does not, but database.dump and state.tar.zst do. The backup belongs on encrypted storage, away from the host it was taken from, and it is worth restoring it into an isolated environment now and again to find out whether it actually works.

The hosts

The panel generates the exact commands per host and per family under Add host: the repository, the package, the fleet CA with its fingerprint to compare, the enrollment and the start. Use those - they carry this installation's own addresses, its one-time token and the CA the fleet really uses. The shapes below are here so that an operator knows what is being run.

StepWhat it does
repositoryAdds the signed repository and its key to apt, dnf or pacman.
packageInstalls flotestro-agent, which brings the helper with it.
CAWrites the fleet CA where the agent reads it, and prints its fingerprint to compare.
enrollSpends the one-time token and takes the host's own certificate.
startsystemctl enable --now flotestro-agent.

From the signed repository

sudo install -d -m 0755 /etc/apt/keyrings
curl -fsS https://ultherego.github.io/Flotestro/packages/flotestro-repo.asc | sudo tee /etc/apt/keyrings/flotestro.asc >/dev/null
echo 'deb [signed-by=/etc/apt/keyrings/flotestro.asc] https://ultherego.github.io/Flotestro/packages/deb stable main' | sudo tee /etc/apt/sources.list.d/flotestro.list >/dev/null
sudo apt update && sudo apt install flotestro-agent

Every index is signed by the release key, and there is no version in any of those lines: apt update is how a host learns a newer version exists and apt upgrade is what moves it. A pre-release goes to a testing channel that a host asking for stable never reads. dnf and pacman read the same tree under rpm/stable and arch/stable. One pacman database serves one architecture, so arch/<channel> is the x86_64 repository and any other architecture stands in arch/<channel>/<architecture> for a host configured by hand.

Without a route out

The file name carries the version, so there is no latest URL to quote; gh resolves the newest stable release itself, and pre-releases are not in it.

curl -fsS https://ultherego.github.io/Flotestro/packages/flotestro-repo.asc | gpg --import
gh release download --repo ultherego/Flotestro --pattern 'flotestro-agent_*_amd64.deb' --pattern 'SHA256SUMS*'
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
sudo apt install ./flotestro-agent_*_amd64.deb

gh attestation verify flotestro-agent_1.2.3_amd64.deb --repo ultherego/Flotestro

Enrollment

sudo tee /var/lib/flotestro-agent/ca.pem >/dev/null   # the fleet CA; compare the fingerprint with the panel
sudo sed -i -e 's|^  enrollment_url: .*|  enrollment_url: "https://panel.example.org:8444"|' \
            -e 's|^  gateway_urls: .*|  gateway_urls: ["https://panel.example.org:8443"]|' /etc/flotestro/agent.yaml
echo "$TOKEN" | sudo -u flotestro-agent flotestro-agentctl enroll
sudo systemctl enable --now flotestro-agent
flotestro-agentctl diagnose                            # explains a host that does not show up

The token is one-time and short-lived

Pass it by file or on standard input, never in the environment: sudo -u flotestro-agent flotestro-agentctl enroll --token-file /run/token, and delete the file afterwards. The daemon itself never enrolls - FLOTESTRO_ENROLLMENT_TOKEN in its environment is ignored and reported at every start until it is removed.

A host that already holds an identity keeps it: a package upgrade does not re-enroll, and an enrollment onto a host that carried a previous installation is refused with machine_already_enrolled - a new fleet CA does not recognise certificates the previous one issued. Remove the identity explicitly first; the sanitisation is in the golden-image runbook.

A machine that is a copy of another answers duplicate_machine_id at the certificate step or machine_id_mismatch at the token step: the host row is keyed by /etc/machine-id, and two machines sharing one are one host as far as the panel is concerned.

For a whole inventory at once there is an Ansible role in ansible. For machines started from an image, the agent package installs flotestro-enroll.service, which runs on the first boot only - when identity/current/agent.pem does not exist - so every clone enrolls as a host of its own.

A site behind a relay

Create relay.yaml and relay-ca.pem next to compose.relay.yaml before the first start: a bind mount whose source does not exist becomes a directory. Then register the relay with a one-time token from the panel and start it; the token file is deleted afterwards.

docker compose -f compose.relay.yaml --profile enroll run --rm relay-enroll
docker compose -f compose.relay.yaml up -d

relay.yaml

schema_version: 1
relay:
  name: "relay-waw-01"
  site: "warsaw"
  listen: "0.0.0.0:8453"
  advertised_names:
    - "relay-waw-01.example.com"
  state_dir: "/var/lib/flotestro-relay"
  buffer_max_bytes: 268435456
upstream:
  enrollment_url: "https://enroll.flotestro.example.com"
  gateway_urls:
    - "https://gateway-a.flotestro.example.com:8443"
    - "https://gateway-b.flotestro.example.com:8443"
  bootstrap_ca_file: "/etc/flotestro/bootstrap-ca.pem"

The relay is configured by that file and by nothing else; flotestro-relay config show prints what it resolves to. Its site is an expectation - the scope a relay really has is the one its enrollment token granted. No relay may advertise a name that is in FLOTESTRO_ADVERTISE. Its spool is on disk and survives a restart, so give the filesystem room: spool.max_bytes is 1 GiB by default and nothing is appended below spool.min_free_bytes, 256 MiB.

The air-gapped profile

An isolated site receives the release on media and nothing else. Four images cross the gap: the control plane, the package repository (the fleet installs its agents from it and from nowhere else), the admin tools (a site that cannot pull an image cannot improvise one on the day it has to restore) and, where the site has one, the relay. PostgreSQL is the site's own, from whatever channel it already trusts for its databases.

On the connected side

Verify the identity of each image first, then take it: a signature checked after the crossing would be a signature checked against a transparency log the site cannot reach.

for name in control-plane package-repository admin-tools relay; do
  reference="ghcr.io/ultherego/flotestro-$name:$version"
  cosign verify \
    --certificate-identity-regexp '^https://github\.com/ultherego/Flotestro/\.github/workflows/images\.yml@refs/tags/v' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com "$reference"
  docker pull "$reference"
  docker save -o "flotestro-$name-$version.tar" "$reference"
done

Then write down what the isolated side is to check, and sign it with the same GPG key the packages are signed with - that key is the one trust anchor the site already has, and the only one that survives a gap. Record the image id, not the registry digest: docker save writes an archive of its own and docker load gives the image a new manifest, so the sha256: the release printed does not survive the crossing, and compose.pins.yaml is not usable there. A site with a local registry has the other option - skopeo copy keeps the manifest and then the digest pin works as everywhere else.

On the isolated side

gpg --import flotestro-repo.asc
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum --check --strict SHA256SUMS
for archive in flotestro-*.tar; do docker load -i "$archive"; done
# then compare each loaded image id against the signed IMAGE-IDS file

The images keep their ghcr.io/ultherego/... names although the site cannot reach that registry. That is deliberate: docker load restores an image under exactly the name it was saved with, the Compose files name it the same way, and an image renamed at the gap is one nobody can match against what was signed. Nothing pulls, because every reference already resolves locally.

Pointing the panel at the local repository

cat >> .env <<'SETTINGS'
FLOTESTRO_PACKAGE_REPOSITORY_URL=http://panel.site.example.org:8090
FLOTESTRO_VULN_NVD_URL=
SETTINGS

docker compose --profile airgap up -d

The panel does not serve the repository and does not proxy it: it composes the "Add host" commands from one address and the hosts fetch from that address themselves, so it is the address the hosts reach - never a Compose service name. Left empty, it leaves a placeholder in those commands and the Add host screen says so in a warning; it is not a setting the panel guesses. NVD is read from a live API and has no offline form, so an isolated site clears it rather than letting a timer fail every six hours.

Plain HTTP is not a weakness there. What a package manager trusts is the signature over the index and the key it imported once, and a package is verified on an isolated site exactly as it is anywhere else. A site that wants TLS puts the same edge in front of port 8090 as in front of the panel.

What an isolated site loses, and what it does not

Everything the fleet is managed with keeps working: inventory, tasks, campaigns, monitoring and its rules, the audit trail, backups, agent upgrades from the local repository. The vulnerability assessment is local too - the hosts report their package lists, the panel compares versions with dpkg and rpm rules of its own, and the feed snapshots live in the database. What it loses is fresh feed data: the status block vulnerability_feeds answers unknown while no feed has ever been read and failed once a snapshot is older than FLOTESTRO_VULN_MAX_SNAPSHOT_AGE (six hours by default). Per host, feed_stale still produces findings while feed_missing produces none at all - and the panel says in as many words that zero findings there means nothing could be checked.

Verification

  • GET /api/v1/status: the schema is current, the database answers, and the instance claims its gateway identity.
  • GET /api/v1/hosts: every enrolled host is online and reports its distribution and its agent version.
  • One operation end to end on one host - a read is enough - reaches a terminal state with a result, not a refusal.
  • The panel shows no bootstrap token warning, and ./bootstrap-token is deleted.
  • The backup pair exists and has been restored once, somewhere that is not production.

Rollback, upgrades and removal

Nothing here is irreversible until hosts are enrolled. Before that, docker compose down -v and an empty database put the machine back. After that, a host is removed by sanitising it - the identity, the task state and the firewall registry - and the panel decommissions its record.

An upgrade is three decisions in one order, and the order is not a matter of taste, because the control plane refuses to serve a schema it does not match in either direction:

  1. Take the pair, with the new images pulled but nothing started from them. A backup taken after the migration is a backup of the version you are trying to leave.
  2. Ask what the new version would do: docker compose run --rm control-plane schema-check. Exit 0 means no migration and the upgrade is a restart; exit 1 with schema_behind means it carries migrations and names how many. Any other answer stops the upgrade.
  3. Migrate once, as its own job, with the migrator's credentials: docker compose run --rm control-plane migrate. Two migrators do not race - the second waits on the advisory lock and says so. Run schema-check again; it must now exit 0.
  4. Roll the replicas one at a time, watching the fleet reconnect between them. The agents are upgraded afterwards and separately, by the panel itself.

Going back has one asymmetry: a version can be gone back to, a schema cannot. If the new version applied no migration, put the previous image back and start it. If it migrated, the old control plane refuses to start with schema_ahead and is right to - going back then means restoring the pair from step 1 and losing everything recorded since. Never delete rows from schema_migrations to make the two agree; the tables are still the new ones and the panel would write into a shape it misreads.

Removing an installation for good is deliberate and in this order: decommission the hosts while the panel still runs, so each one stops trusting the centre and revokes its own certificate; take a last backup pair if the audit trail has to outlive the panel; docker compose down --volumes, which takes the state volume with it; and then the database, if it is one this installation owns. What remains on a managed host is the agent package itself, which apt purge, dnf remove or pacman -Rns removes together with its identity files.

down keeps the volumes on purpose

A plain docker compose down stops the containers and leaves the state and the database where they are, because an operator stopping a panel for an hour must not lose the fleet's certificate authority by typing the usual command. Only --volumes takes the state.
