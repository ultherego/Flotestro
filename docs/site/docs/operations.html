6. Operations reference

Flotestro has no “run this command” action. Every change and every read is one of 128 typed operations, each with its own permission, its own risk level, its own lock on the host and its own payload. This page is the whole registry, transcribed from internal/opspec/; the panel serves the same list at GET /api/v1/actions.

How to read an entry

Every operation declares the same facts. They are not advice: the panel, the agent and the root helper all decide by them.

FactWhat it decides
PermissionThe permission an operator needs, in the scope of the host. Without it the order is refused before anything is sent.
AdapterThe capability the host must report for the operation to be possible there. A host without it is excluded rather than failed.
RiskWhat the operation threatens. Critical and destructive operations require fresh authentication; a destructive one also requires typing the target name.
Lock classThe host resource the operation holds exclusively while it runs. Two operations of the same class never run on one host at once.
Campaign modeWhether the operation may run on many hosts at once, and on what terms.
Offline policyWhat a campaign does with a host that is not connected when its turn comes.
Default timeoutHow long one attempt may take before the host gives up on it.
Output limitThe largest result the operation may send back. Past it the result is cut.
VerifierThe read of the host that confirms the change after the apply. Only it turns the change into a success.
PlanWhether the operation must not be ordered without a plan approved by a human, and which read computes that plan.
CancelWhat a cancel does to an operation that is already under way.
RollbackWhat way back exists after the change landed.
RetryWhether repeating the same thing can succeed.

Risk levels

ValueMeaning
lowA read or a plan: it changes nothing.
mediumChanges state reversibly and locally.
highInterrupts a service or changes the content of the system.
criticalCan cut off access to the host or change its identity. It requires fresh operator authentication.
destructiveDestroys data irreversibly. It requires typing the target name and by default does not run in bulk.

An operation the registry does not describe is not a safe operation: an unknown type is treated as critical rather than as the lowest level. The risk of one order can be higher than the registry's level for the operation: an order that creates an account in a privileged group, or moves one into it, is critical whatever the operation says.

Fresh authentication and typing the target

A critical or destructive operation requires the operator to confirm their identity right before ordering. A destructive operation also requires the operator to type the target name - the hostname, or for the deletion of a local account the name of that account. Three operations that destroy no data require the same typing, because a click is not decision enough for them: system.shutdown (nobody will power this host back on through the panel), system.hostname.set (every system that knows the host by name loses it at once) and identity.host.leave (every directory account loses the host at once, and the join back needs a new credential from the directory).

Permissions an order needs beyond the operation’s own

PermissionWhen the order needs it
schedule.root.execA scheduled entry whose user is root.

Lock classes

A lock class names the host resource an operation uses exclusively. An operation with no class names none.

ValueMeaning
packagesThe package manager of the host.
unitsThe systemd units.
containersThe container engine.
identityThe host's domain membership and its keytabs.
accountsThe local accounts.
networkThe network is one host resource: two parallel configuration changes would leave a state that neither rollback plan describes.
storageStorage is one resource: two parallel operations on the same filesystem can damage it.
backupA backup repository is one resource: the tools hold their own lock on it.
certificatesThe trust store is one per host, and the tool that recomputes it rewrites the whole bundle.
hostThe whole host: a rename collides with every other mutation the same way a reboot does.

Beside the registry's lock class the agent takes resource claims of its own. Two of them are shared rather than exclusive, and carry a bounded weight on one host: logs-read (reading the journal and log files: bytes per second and file descriptors) carries 4 at once, and inventory-heavy (reads that start subprocesses and walk the host: process, container and storage scans) carries 2. The exclusive claims that are not lock classes are host (a reboot or a shutdown collides with every other mutation), kernel (sysctl and modules; such a change takes the network as well, because it changes the network stack), security (the MAC mode and the audit rules) and file (one managed file).

Campaign modes

A campaign is the same operation on many hosts. Whether one is allowed, and on what terms, is a declaration of the operation; a missing declaration is a refusal.

ValueMeaning
noneNot allowed in bulk.
same_payloadThe same payload means the same thing on every host.
per_host_planA shared target state from which every host computes its own plan.
specializedAn operation with its own state machine: a reboot is settled by the host coming back, enrollment has its own stages.

A campaign of an operation that computes a per-host plan starts with the read that computes it. The wave size and the concurrency a campaign begins with when the order names neither are 10 hosts and 5 at a time, except for packages.repository.set (50 and 5) and system.hostname.set (10 and 2).

Offline policies

What a campaign does with a host that is not connected when its turn comes. A campaign may only tighten the policy an operation declares, never loosen it.

ValueMeaning
require_onlineEnds the host's participation the moment it is found offline: the order is reactive or contextual, and the state it was given for will not be there when the host comes back.
skip_if_offlineLeaves the host out without calling that a failure: a read or a refresh that did not happen is a gap in knowledge, not a broken change.
wait_until_deadlineKeeps the host in the queue without a slot and starts it when it comes back, up to the campaign's deadline.
replan_on_reconnectWaits the same way, but computes the host's plan again after the reconnect and runs the change only when the plan is the one that was approved.

Fan-out reads

A fan-out is one diagnostic read across many hosts at once. It is for reads only - a change on many hosts is a campaign - and every read that may fan out declares its ceiling.

A read outside the table does not fan out and is run host by host. A live view of the journal (journal.follow) is refused as a fan-out for a reason of its own: it holds a process on the host for as long as it lasts.

Verification and the way back

A change is not a success because the command returned zero. The host reads itself afterwards with the verifier the operation declares, and only that turns the change into a success. A change the verifier could not confirm is reported as applied_unverified; three operations go further and put the previous state back by themselves rather than leaving an unconfirmed change standing: sysctl.ensure, file.ensure and file.rollback.

What a campaign checks on the host after the change:

ValueMeaning
noneNothing to check, or nothing that can be checked from the panel.
unit_healthThe unit the change concerns is in the expected state and healthy.
connectivityThe host still answers on the management channel.
plan_recheckThe plan computed again shows no difference.
customThe module has its own check - a probe, a boot ID, a version reported back.

What way back exists once the change landed:

ValueMeaning
automatic_localThe host reverts itself without the control plane - the connectivity watchdog of the network and firewall modules.
exact_restoreA previous version is kept and can be put back as it was - a managed file, a schedule, a Compose manifest.
compensatingA new plan neutralises the effect, but the history stays - a downgrade after an upgrade, a start after a stop.
best_effortAn attempt to limit the damage with no guarantee of the initial state.
noneIrreversible - a wipe, a shutdown, a signal.

Five changes have a named operation that undoes them: file.ensure → file.rollback, network.profile.apply, network.link.apply and network.link.remove → network.rollback, and firewall.rule.ensure → firewall.ruleset.restore.

What a cancel does to an operation under way. A queued operation is always cancellable: it has not touched the host.

ValueMeaning
safeThe context cancel interrupts the operation and leaves a consistent state - a read, a probe, a stream.
checkpoint_onlyThe cancel is checked only between atomic steps. The step under way finishes; the next one does not start.
impossible_after_startOnce the host reported a start, the cancel is only information.
local_watchdog_ownedThe host's own safety mechanism decides.

Whether repeating the same thing can succeed:

ValueMeaning
neverThe same order will fail the same way; a decision is needed.
automaticThe system repeats on its own, e.g. once capacity frees up.
after_changeA retry makes sense once the named thing changed.
after_replanThe plan has to be computed again and approved again.
read_stateRead the state of the host first; never repeat a destructive step blind.

A deprecated operation

localuser.sshkeys.set has been replaced by localuser.sshkeys.replace_all: the same semantics and the same risk, with the expected list optional in the older one.
