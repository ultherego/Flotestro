Flotestro documentation

Flotestro manages a fleet of Linux servers from one panel: it plans a change, has it approved, carries it out on the hosts and records what happened. This manual is the reference for the people who run it - what the parts are, how they are installed, what the panel promises, and what every refusal means.

Read it in order the first time. Introduction and How a change happens are the two chapters the rest rests on: everything the panel does is a typed operation, a plan, an approval bound to a digest, a dispatch and a result. After that the reference chapters answer single questions - what this variable does, what this operation needs, what this code means.

Chapters

1. Introduction

What the product is, what it manages, and the things it deliberately does not do - no shell on a host, no external monitoring stack, no guessing at a fact the host could not report. The doctrine is here: unknown is never zero, every operation is a typed contract, the host reports facts and the panel judges, a plan is approved by digest, every refusal has a stable code, fail-closed.

2. Architecture

The five parts - the control plane, the unprivileged agent, the root helper, the site relay and PostgreSQL - with the ports between them, the identity each one proves, and the state directory that is not in the database. It also answers why the agent is a native package and the control plane is an image.

3. Installation

The long form of an installation from nothing: the control plane from its image or from packages, the first administrator and the group mappings without which nobody can sign in, the backup pair taken before the fleet exists, hosts from the signed repository, a site behind a relay, and the air-gapped profile.

4. How a change happens

One change end to end: the operation, its plan, the approval bound to a digest, dispatch, the lease, the result and the verifier - and what a campaign adds on top of it: a snapshot, a canary, waves, maintenance windows and budgets. Inventory with its revisions and cadences, and the audit chain that flotestro-auditverify checks without the database.

5. Configuration reference

Every environment variable of every binary, its default, whether a change needs a restart, and what it costs in security to change it.

6. Operations reference

The typed operations: what each one does, the permission it needs, its risk level and lock class, whether it takes part in a campaign, and the refusals it can answer with.

7. Errors and refusals

The stable codes. A refusal is part of the contract: the same situation always answers with the same code, in the API, in the panel and in the audit trail. The running panel serves the same list at GET /api/v1/errors.

8. API

The REST API under /api/v1: authentication, permissions, concurrency with If-Match, and the routes themselves.

9. Runbooks

The procedures the panel does not carry out by itself - CA rotation, a database restore, a queue that is not moving, a relay out of room, a gap in the charts, quarantine and decommission, a support bundle, a golden image. Each one names its signals, its preconditions, the exact requests, the verification and the way back.

How to read it

A refusal code
Written as machine_already_enrolled. It is the stable identifier of one reason, not a message; the wording of the message may change, the code does not.
A default
Given wherever there is one, as the product ships it. A setting with no default is marked required, and the binary refuses to start without it.
A command
Runs where the text says it runs: on the panel host, inside the container, or on the managed host as root. The panel writes the host commands for its own addresses under Add host; the shapes in this manual are there so an operator knows what is being run.
A permission
Written as pki.rotate. Permissions are granted to roles, roles to groups of the identity provider, and each grant is scoped by site and environment.

Where this manual ends

Everything here can be pointed at in the repository. Where a procedure has no route and no command, the manual says so rather than inventing one: there is no API that exports the database, and no route that pulls a support bundle off a host.
