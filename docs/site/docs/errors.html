7. Errors and refusals

Every refusal, failure and skip the panel, the agent and the helper can put on a task, a campaign target or a request carries a stable code. A code answers two questions: what happened, and what can safely be done next. This page is the whole guide, 260 entries, transcribed from internal/opspec/errors.go; the panel serves the same list at GET /api/v1/errors.

The wording is the panel’s own

The meaning and the action are quoted exactly as the panel shows them, so a code searched for here reads the same as the one on the screen. An unknown code gets no guide at all: the panel shows the code as it came rather than inventing advice.

The retry policy

Every entry carries a retry policy. It is the answer to “may this be repeated” when the outcome is a failure or unknown.

PolicyMeaning
neverThe same order will fail the same way; a decision is needed.
automaticThe system repeats on its own, e.g. once capacity frees up.
after_changeA retry makes sense once the named thing changed.
after_replanThe plan has to be computed again and approved again.
read_stateRead the state of the host first; never repeat a destructive step blind.

Whether a code counts as a failure

A code either raises the failure rate of a campaign or it does not. An excluded or skipped host is visible but not a failure, so it never trips the threshold that pauses a campaign. Every entry below says which it is.

Stage: planning

11 codes.

campaign_mode_unsupported

The operation has no bulk mode in the registry.

What to do Run it host by host, or deploy an adapter that declares a campaign mode.

retry: never not a failure

directory_plan_incomplete

The approved change carries no reference to the entry it would move - where it is, which entry it is and when it last changed - so there is nothing to bind the execution to.

What to do Plan the change again; the new plan records the entry, and the execution refuses if that entry moves between the approval and the change.

retry: after_replan not a failure

docker_object_conflict

The object on the host differs in a setting the engine cannot change in place - a volume's driver or driver option, a network's address range - so bringing it to the description means destroying it and creating it again. A volume recreated is a volume emptied, and the order did not say it accepts that.

What to do Read the change list of the plan. Declare the object the way it already stands, give the new one another name, or order the change again with force once the data in it is accounted for.

retry: after_change counts as a failure

image_digest_unresolved

A Compose service or a declared container names its image by a tag the host could resolve to a digest neither at the registry (no network, or a private registry the host is not logged into) nor among the images already on the host. The plan binds digests, so it was not computed.

What to do Pin the digest in the description (image@sha256:...), pull the image on the host first, or give the host access to the registry; then plan again.

retry: after_change counts as a failure

not_a_campaign_action

The operation is excluded from campaigns on purpose.

What to do Run it host by host with an operator present.

retry: never not a failure

offline_policy_loosened

The request asked for a weaker offline policy than the operation declares.

What to do Keep the operation's policy or tighten it; it may not be loosened.

retry: never not a failure

plan_changed_offline

The host came back with a state that gives a different plan than the one approved.

What to do Read the new plan and order a campaign that approves it; the consent covered the old one. Not a failure.

retry: after_replan not a failure

plan_create_failed

The planning job could not be created.

What to do Check the panel log and order again.

retry: after_change not a failure

plan_failed

The planning operation failed on the host.

What to do Look at the plan job; fix the host and plan again.

retry: after_change not a failure

plan_hash_missing

The host gave no plan digest, so nothing can be approved.

What to do Update the agent; a plan without a digest cannot be bound to a consent.

retry: after_change not a failure

plan_refused

The host computed the plan and refused the change with a reason.

What to do Read the reason; the host will not take this change as it is.

retry: never not a failure

Stage: preflight

13 codes.

boot_filter_unsupported

The read asked for one boot of the host and the agent of the host does not apply a boot filter: an older agent would ignore it and answer with every boot under the name of one, so the read was not sent.

What to do Read the journal without the boot filter and narrow it by time, or upgrade the agent on the host; not a failure.

retry: after_change not a failure

capability_missing

The host has no adapter for this operation.

What to do Exclude the host or install what the adapter needs; not a failure.

retry: after_change not a failure

capability_unknown

The host has not reported its adapters yet.

What to do Wait for the host to connect and report; not a failure.

retry: after_change not a failure

checker_failed

The tool a check proves a fact with is on the host but returned no status: it did not start, or it did not finish in time.

What to do Read the reason the host sent with the fact, mend what it names, and order the module read again. Not a failure.

retry: after_change not a failure

checker_missing

The host has not got the tool a check needs for its proof - visudo for the sudoers files - so that fact was never proved on this host.

What to do Install the tool on the host; until then the check stays unknown instead of passing. Not a failure.

retry: after_change not a failure

conflict

Another campaign already works on this host.

What to do Nothing; the host waits for the other campaign's lock.

retry: automatic not a failure

directory_moddn_unsupported

The preflight asked the directory what it can do and it proved it cannot preserve an account: the connector's service account may not move an entry, or the container of preserved accounts is not there. Nothing was ordered and the local account was not touched.

What to do Run the directory provisioning step for preserving accounts: it gives the connector's service account the four rights the move needs - System: Preserve User for the move itself, System: Modify User RDN for the name it carries, System: Read Preserved Users so the directory can report what it moved, and System: Modify Preserved Users because the directory clears the password of the entry it preserves - through the privilege Flotestro Preserve Users and the role Flotestro Directory Connector, and nothing else. It is safe to repeat - a second run changes nothing. If the directory refuses the connector that step too, the refusal names the ipa commands a directory administrator runs instead. A directory that merely does not report its rights does not raise this.

retry: after_change not a failure

inventory_stale

The module a policy or a campaign judges the host from was read more than twice its cadence ago; a verdict on it would describe a host that has been silent, not the host as it is.

What to do Refresh the named module - order its read, or find out why the host stopped reporting; until then the verdict is unknown. Not a failure.

retry: after_change not a failure

out_of_scope

The host lies outside the operator's scope.

What to do Ask somebody with the scope, or narrow the selector.

retry: never not a failure

quarantined

The host is quarantined and takes no operations.

What to do Release the quarantine first.

retry: after_change not a failure

recovery

The host is recovering its identity and takes no operations until the new certificate connects.

What to do Finish the recovery on the host; the state ends by itself with the first session of the new key. Not a failure.

retry: after_change not a failure

retired

The host is retired and takes no operations.

What to do Nothing; a retired host does not come back. Enroll the machine as a new host once its retention has passed. Not a failure.

retry: never not a failure

retiring

The host is being decommissioned and takes no operations.

What to do Nothing; the host is leaving the fleet. Not a failure.

retry: never not a failure

Stage: admission

38 codes.

account_without_credential

The order would create an account with no key and, since the panel sets no passwords, no way to log in - and did not say so.

What to do Give the account a key, or set inactive: true to create it deliberately without a way in; the panel then shows it as locked.

retry: after_change not a failure

array_lifecycle_out_of_scope

The order asks the panel to create or destroy a software array. The panel manages the members of an array that exists and nothing beyond that: which arrays a machine has is a decision about its whole disk layout, taken when the machine is built.

What to do Build or destroy the array on the machine itself; the panel will read it, judge it and manage its members afterwards.

retry: never counts as a failure

blocked_upgrade_required

The host's agent predates a proof this installation requires: behind a relay under FLOTESTRO_RELAY_IDENTITY=enforce it does not sign the identity envelope (relay.identity v2), or it renews or fetches a secret through a relay without the host's proof.

What to do Upgrade the agent on the host - the relay did its part. Until then the host connects directly if it can, or stays refused; not a failure of any change.

retry: after_change not a failure

bond_needs_two_members

The bond would have fewer than two members. With one it carries the same traffic over the same cable with a driver in between, and none of the redundancy a bond exists for.

What to do Name at least two members, or set the address on the interface directly instead of bonding it to itself.

retry: after_change not a failure

budget_capacity

The named budget has no free token.

What to do Nothing; the host starts when a token frees up. Raise the budget if it should not wait.

retry: automatic not a failure

budget_fair_share

This campaign already holds its share of the budget.

What to do Nothing; it is promoted by age. Raise the budget if it should not wait.

retry: automatic not a failure

docker_network_predefined

The order is about bridge, host or none: networks of the engine itself. The engine does not allow removing or recreating them, so the panel does not offer it.

What to do Declare a network of your own and attach the containers to it; the built-in ones stay as the engine made them.

retry: never counts as a failure

global_silence_denied

A global silence - the one that may keep back the security alerts of the installation - was ordered by an identity that manages the notification channels of one site at most. Nothing was written and no alert was kept back.

What to do Silence the host or the rule instead, or have somebody who manages the notification channels of the whole installation order the global silence and say in its reason why the security alerts are being kept back.

retry: never not a failure

managed_timers_unsupported

The agent of this host reads systemd timers but does not write them: its schedules adapter does not name the managed_timers feature. An order for a timer would be ignored there and written as a cron entry under the name of a timer, so it was refused instead.

What to do Order the entry as a cron entry, or upgrade the agent on the host and order the timer again.

retry: after_change not a failure

metrics_retention_shrink_unacknowledged

The monitoring settings offered would drop readings the panel still keeps - whole daily partitions of raw samples, or rollups, recorded gaps and clock corrections - and the request did not say that this is intended. Nothing was stored and nothing was deleted.

What to do Read what the preview says goes: it is counted before anything is written and it cannot be undone afterwards. Send the same values again with acknowledge_data_loss set, or raise the retention back.

retry: after_change not a failure

payload_permission_missing

The content of the order asks for more than the operation's own permission: an entry for root needs schedule.root.exec, a write allowed to skip its validator needs file.write.unvalidated. The panel refused the order before it became a job.

What to do Change the order - a service account instead of root, a write with its validator - or have a principal with the permission place it.

retry: never not a failure

preview_action_mismatch

The preview was taken for a different operation. What qualifies a host depends on the operation, so the eligible hosts of one are not those of another.

What to do Preview the operation you are ordering and place the order from that answer.

retry: after_change not a failure

preview_consumed

The preview named by the order already created a campaign. One approved picture of the fleet orders one campaign, so a repeated order does not quietly create a second.

What to do Look for the campaign that preview created. If another one is really wanted, preview again and order from the new answer.

retry: after_change not a failure

preview_digest_mismatch

The preview named by the order is not the preview it was answered with: the identifier and the fingerprint describe different pictures of the fleet.

What to do Preview again and order from a single answer, carrying its identifier and fingerprint together.

retry: after_change not a failure

preview_expired

The preview stood longer than a preview stands, so what it counted is no longer a description of the fleet.

What to do Preview the selector again and order from the new answer.

retry: after_change not a failure

preview_permission_mismatch

preview_required

This panel requires a campaign to be ordered from a preview, and the order named none. The preview is what binds the order to the set of hosts somebody actually read.

A notification channel cannot send as it is: it was disabled while its messages waited, its configuration does not read, or the panel has no sender for its kind.

What to do Enable or correct the channel and retry the dead letters; the messages of a channel that is to stay disabled can be left as they are.

retry: after_change not a failure

delivery_attempts_exhausted

The receiver of a notification channel kept failing in a way that passes - a 5xx, a 429, an unreachable address - until the attempts ran out. The message is a dead letter. Deliveries written before this release carry this code; a delivery written now carries the transport's own reason instead, and its state says the queue gave up.

What to do Bring the receiver back or fix the address, send a test from the channel, then retry the dead letters; nothing was lost.

retry: after_change not a failure

permanent_http_error

The receiver of a notification channel answered a status that is neither a success nor one that passes - a 404, a 400 - so the address or the shape of the message is wrong for it. The message is a dead letter.

What to do Check the address and what the receiver expects; send a test from the channel; then retry the dead letters.

retry: after_change not a failure

permanent_smtp_error

The mail relay refused the message with a permanent reply (5xx): a sender or a recipient it does not accept, a message it will not take. The message is a dead letter.

What to do Read the reply on the delivery, correct the sender or the recipients on the channel, send a test, then retry the dead letters.

Stage: directory

2 codes.

directory_refused

The directory refused the change and named its own reason. Nothing was changed locally: the directory goes first exactly so that its refusal does not leave a host denying a user the directory still holds.

What to do Read the directory's reason in the phase - an ACI, a validation, an entry that is not there - correct it in the directory and order again.

retry: after_change not a failure

directory_unreachable

The directory did not answer, so nothing is known about what it would have done and nothing was changed anywhere.

What to do Check the connector on the identity screen - the keytab, the KDC, the directory itself - and order again once it answers.

retry: automatic not a failure

Stage: provisioning

1 codes.

directory_provisioning_incomplete

The step that gives the connector's service account the right to move an entry into the container of preserved accounts could not finish on its own: the directory refused the connector one of the objects, or it does not publish the permission that carries the ACI at all. Nothing was half-granted - the step stops at the first refusal and every object it did create is one it may create again without effect.

What to do The report names the exact ipa commands, in order, for a directory administrator to run, or the ACI to add when the directory does not publish the permission - a permission cannot express moddn, so that one is added with an LDAP client. Run the step again afterwards; it changes nothing that is already in place and confirms with the directory's own answer about the move.

crypto_state_ambiguous

The installation has no record and what exists does not add up to either an empty installation or a complete old one.

What to do Read the reason in the log: restore the missing part of the state directory, or clear a leftover of an abandoned installation. See docs/runbooks/db-restore.md.

feed_release_missing

A fetch of a vulnerability feed stopped covering a release the snapshot in force covered, so it was not activated.

What to do Check the feed URL and the release list on the Vulnerabilities screen; accept the fetch there if the release really went out of the feed. Hosts of that release would otherwise all read as clean.

retry: after_change not a failure

feed_shrank

A fetch of a vulnerability feed carried far fewer findings than the snapshot in force, so it was not activated.

What to do Compare the two counts on the Vulnerabilities screen; accept the fetch there if the vendor really retired the findings, otherwise fix the source. The previous snapshot stays in force and ages into stale.

retry: after_change not a failure

gateway_id_in_use

Another control-plane instance is alive under this FLOTESTRO_GATEWAY_ID and is still renewing its heartbeat. Two replicas under one identifier are read as one instance by the job leases, the session fencing and the audit trail.

What to do Give this replica an identifier of its own - every replica has a unique FLOTESTRO_GATEWAY_ID and they share the database - or stop the instance the log names. A record of an instance that is gone is taken over by itself within a minute.

retry: after_change not a failure

installation_state_mismatch

The state directory and the database are not one installation: they name two different ones, or one of them names none while the other has a history. The log says which of the two is the stranger.

What to do Never scale the control plane with separate state volumes against one database - two state directories mean two fleet CAs and two secret store keys for one installation. Give the replica the state directory of this installation, or point it at the database that belongs to the directory it has.

issuer_key_unavailable

The certificate of the fleet CA is there and its private key is not, or the installation records a CA and the state directory holds none.

What to do Restore ca.key (and ca.pem) from the backup of the state directory; a new CA would cut every host off. See docs/runbooks/db-restore.md.

retry: after_change not a failure

metrics_retention_too_short

The raw retention is shorter than the window the panel offers at full resolution plus the longest a sample may take to arrive. Such a configuration deletes a reading a relay is still carrying, by definition and without anybody ordering it, so the panel refuses to start on it and refuses to store it from the settings screen.

What to do Raise the raw retention to at least the sum, or lower the raw query window or the maximum lateness. The three are named in the configuration reference under the monitoring settings; nothing was stored, so the values in force are unchanged.

retry: after_change not a failure

pki_state_mismatch

The CA material does not fit together, or the CA on disk is not the one the installation records.

What to do Restore the whole state directory from the backup taken with the database dump; do not mix files of two installations. See docs/runbooks/db-restore.md.

retry: after_change not a failure

relay_certificate_expired

The certificate a relay presents has ended; the centre and the agents refuse it.

What to do Let the renewal succeed - it needs a reachable gateway - or enroll the relay again if the certificate is past recovery.

retry: after_change not a failure

relay_certificate_unknown

A relay holds no end date for its own certificate, so it cannot say whether the certificate is valid and does not report itself ready on the strength of not knowing.

What to do Inspect the state directory of the relay; an identity without an end date means the saved material is incomplete and the relay has to be enrolled again.

retry: after_change not a failure

relay_listener_unavailable

The listener of the agents of a relay is closed or has refused every connection for longer than its grace period: the process runs but no longer serves its site.

What to do This is the one relay failure a restart answers. Read the detail for the cause - file descriptors, a port taken - before the restart, because it comes back otherwise.

retry: automatic not a failure

relay_spool_unwritable

The spool of a relay cannot reach its disk: a sync of the segment file failed. What the relay takes now is not what it holds after a power failure.

What to do Look at the filesystem of the state directory of the relay - full, read-only or failing - and at the disk under it. The relay reports itself not ready until a sync succeeds again.

schema_ahead

The database carries migrations this binary does not know: a newer control plane has already migrated it. Swapping the image back does not undo a schema.

What to do Deploy the version that migrated this database, or restore the backup of the database and of the state directory taken before the upgrade. Never delete rows from schema_migrations to make the two agree.

retry: after_change not a failure

schema_behind

The database misses migrations this binary carries, and this process does not bring the schema forward itself. A control plane serving a schema it does not match would answer with tables that are not there.

What to do Run the migrate command as its own job, with the credentials of the migrator, and start the serving replicas afterwards; schema-check answers whether it worked. A single-host installation may instead leave FLOTESTRO_AUTO_MIGRATE at true.

retry: after_change not a failure

secret_source_invalid

The panel refused to start because a secret is configured in a way it will not read: the variable and its _FILE form are both set, the variable is set but empty, or the file the _FILE form names is a symlink, a directory, a pipe, a socket, a device, larger than 64 KiB, owned by somebody else, or readable by the group or by others. A secret that reaches the process as an environment variable is readable in the inspection output of the container engine, in the shell history and in every child process, which is why the file form exists.

What to do Mount the secret as a regular file owned by root or by the service user with mode 600 and point FLOTESTRO_..._FILE at it, or set the plain variable alone - never both. The message names the variable and the path; it never names the value.

retry: after_change not a failure

secrets_key_unavailable

The installation has secrets or a recorded key, and the key that opens them is missing or is not the installation's.

What to do Restore keys/<key-id>.key (or secrets.key) from the backup of the state directory; never generate a key in its place. See docs/runbooks/db-restore.md.

retry: after_change not a failure

support_bundle_unsealed

This panel holds no key material, so it can neither seal a new bundle nor open one that is sealed. A bundle readable without a key is not one this panel writes.

What to do Bring the installation's key provider back - the key file or the credential the panel was started with - and ask again.
