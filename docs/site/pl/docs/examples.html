11. Przykłady użycia

Wykazy mówią, czym jest każda trasa i każda operacja. Ta strona jest drugą połową: wywołaniami, które można wkleić do terminala, i tym, co na nie odpowiedziało. Każde żądanie i każda odpowiedź poniżej zostały wykonane na działającej instalacji — identyfikatory pochodzą z tego przebiegu, więc u Ciebie będą inne.

Co jest potrzebne: adres i token

Panel odpowiada na FLOTESTRO_ADMIN_ADDR, domyślnie 127.0.0.1:8080, czystym HTTP za czymkolwiek, co terminuje dla niego TLS. Nic poniżej nie wymaga przeglądarki.

Świeża instalacja zapisuje jeden token w swoim katalogu stanu, jako bootstrap-token. We wdrożeniu kontenerowym ten katalog jest wolumenem, więc plik czyta się z niego, a nie z hosta:

docker compose exec -T control-plane cat /var/lib/flotestro/bootstrap-token

Ten token należy do principala bootstrap-admin i żyje 30 dni. To poświadczenie, którym tworzy się pozostałe: długowieczna automatyzacja powinna mieć własny token, wystawiony własnemu principalowi z własnymi uprawnieniami, przez POST /api/v1/principals/{id}/tokens. Adres i token zostają w powłoce na resztę tej strony:

PANEL=http://127.0.0.1:8080
TOKEN=$(docker compose exec -T control-plane cat /var/lib/flotestro/bootstrap-token)

Token to nie sesja

Oba poświadczenia sięgają tych samych uprawnień, ale sesja przeglądarki jest ograniczona w czasie, nosi nagłówek CSRF i da się ją uwierzytelnić ponownie; tokena nie. Ma to znaczenie przy tych kilku operacjach, które wymagają świeżego uwierzytelnienia, a FLOTESTRO_STEPUP_TOKENS=refuse jest sposobem, w jaki instalacja mówi, że token nigdy nie może ich zamówić. Zob. step-up.

Pierwsze wywołanie i kształt listy

Dwa hosty, posortowane po nazwie:

curl -sS -H "Authorization: Bearer $TOKEN" \
  "$PANEL/api/v1/hosts?limit=2&sort=hostname"

Każda lista ma tę samą kopertę. count to ta strona, total to ile pasuje do filtru na wszystkich stronach, a next_cursor jest puste na ostatniej:

  "total": 8,
  "next_cursor": "AgAAAAMAAAAIaG9zdG5hbWUAAAAMYWdlbnQtZGViaWFu...",
  "items": [
    {
      "id": "91010c96-a7ed-4733-91ee-0f06cc7a6482",
      "hostname": "agent-arch",
      "site": "lab",
      "environment": "test",
      "lifecycle_state": "active",
      "os_family": "arch",
      "agent_version": "0.62.0",
      "connection_state": "online",
      "last_seen_at": "2026-10-08T09:40:28.018922Z",
      "agent_build_commit": "7bc2abf369a275d51ed01effafb66be8f28f6594",
      "helper_capability_mode": "enforce",
      "failed_units": 0,

Rekord hosta niesie 35 pól; powyżej są te, po które zazwyczaj czyta się listę. Zwróć uwagę na pending_security_updates: null, nie 0. Host tej liczby nie zgłosił, a panel jej nie wymyśla — i właśnie dlatego sortowanie stawia nieznaną liczbę poniżej zera, a nie między zerami.

Przejście listy do końca

Kursor jest nieprzejrzysty: to klucz sortowania ostatniego wiersza, oddawany dokładnie tak, jak przyszedł. Nie jest offsetem, więc wiersze wstawione w trakcie przeglądania nie przesuwają okna ani nie powtarzają wiersza:

cursor=
while :; do
  page=$(curl -sS -H "Authorization: Bearer $TOKEN" \
    "$PANEL/api/v1/hosts?limit=100&sort=hostname&cursor=$cursor")
  echo "$page" | jq -r '.items[].hostname'
  cursor=$(echo "$page" | jq -r '.next_cursor // empty')
  [ -n "$cursor" ] || break
done

Kursor, którego ten panel nie wystawił, albo wystawiony przy innym sort, zostaje odrzucony — nie jest po cichu czytany jako pierwsza strona.

Zamówienie jednej operacji na jednym hoście

To wywołanie, wokół którego pisze się większość automatyzacji, i ma dwa szczegóły, które warto złapać od pierwszego razu.

Trasa jest per host. Operację tworzy się pod hostem, na którym działa: POST /api/v1/hosts/{id}/operations. Nie ma trasy, która przyjmuje identyfikator hosta w ciele.

Pole nazywa się action w żądaniu i action_type w odpowiedzi. Żądanie nazywa operację w action; rekord zadania, który wraca, raportuje ją jako action_type, bo zadanie ma typ i wersję. Żądanie z action_type to żądanie bez akcji.

Restart usługi na jednym hoście:

HOST=42e2f7c7-8e02-4131-a797-55b5f0f53f54

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: restart-cron-$(date +%s)" \
  -d '{
        "action": "unit.restart",
        "payload": { "unit": { "unit": "cron.service" } }
      }' \
  "$PANEL/api/v1/hosts/$HOST/operations"

201 Created i zadanie tak, jak zapisał je panel:

{
  "id": "904dfe79-8c6c-4b3f-9fc1-ee7638ff5b6f",
  "host_id": "42e2f7c7-8e02-4131-a797-55b5f0f53f54",
  "hostname": "agent-debian",
  "action_type": "unit.restart",
  "action_version": 1,
  "payload": { "unit": { "unit": "cron.service" } },
  "payload_hash": "17af2e027304d8f9737c4e1551b65e3a8ac219f241f1e3eb14b6b4b70bf961f1",
  "state": "queued",
  "requires_approval": false,
  "required_approvals": 1,
  "collected_approvals": 0,
  "preconditions": {
    "os_family": "debian",
    "required_capabilities": [ "systemd" ]
  },
  "timeout_seconds": 120
}

Payload siedzi w nazwanej grupie — "unit": { ... } — i ta grupa jest ta sama dla każdej operacji działającej na unicie. preconditions to panel mówiący, do czego przyciśnie hosta przed wysłaniem pracy; host, który ich nie spełnia, dostaje odmowę, a nie próbę.

Część operacji nie wystartuje na samo żądanie

Operacja o wysokim lub krytycznym ryzyku może wymagać reason (co najmniej 8 znaków), nazwy hosta przepisanej w target_confirmation, zatwierdzenia przez kogoś innego albo uwierzytelnienia nie starszego niż kilka minut. Co dotyczy której, jest w wykazie operacji przy każdej z nich, a odmowa zawsze mówi, czego brakuje.

Odczyt tego, co host zrobił

Rekord zadania niesie stan; próba niesie to, co powiedział host. Najpierw zadanie:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/jobs/$JOB" | jq '{state, finished_at, result_status}'
{
  "state": "succeeded",
  "finished_at": "2026-10-08T09:42:12.636754Z",
  "result_status": "succeeded"
}

Potem próby — tam jest wyjście, kod wyjścia i tożsamość bramki, która to wysłała:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/jobs/$JOB/attempts" | jq '.items[0]'
{
  "attempt_number": 1,
  "status": "succeeded",
  "exit_code": 0,
  "gateway_id": "cp-01",
  "session_id": "1353c457-2ae1-4391-b445-5c0b11091da1",
  "dispatched_at": "2026-10-08T09:42:12.440228Z",
  "started_at": "2026-10-08T09:42:12.446875Z",
  "finished_at": "2026-10-08T09:42:12.636754Z",
  "output_truncated": false,
  "replayed": false,
  "stdout": "2026-10-08T08:17:01+00:00 agent-debian CRON[2351]: pam_unix(cron:session): session closed for user root\n..."
}

Jest jeden rekord na próbę, więc ponowienie nie nadpisuje tego, co powiedziała pierwsza. replayed oznacza odpowiedź, którą panel wziął z własnego rekordu hosta dla żądania już wykonanego, a nie drugie wykonanie. output_truncated mówi, że wyjście uderzyło w max_output_bytes — o więcej prosi się tym polem w zamówieniu.

Zadanie, które się wykonało, ale nie dało się potwierdzić, nie jest raportowane jako sukces: result_status przyjmuje applied_unverified, co znaczy, że zmiana została zrobiona, a weryfikator nie mógł odczytać hosta z powrotem. To stan do obserwowania, nie błąd do ślepego ponawiania.

Skąd bierze się kształt payloadu

Payload jest grupowany po nazwie. Grup jest 43, po jednej na rodzaj rzeczy, na której operacja działa, a operacja czyta dokładnie jedną. Grupy i ich pola są w dokumencie, który panel generuje z własnych tras, więc nie mogą się od kodu rozjechać:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/openapi.json" \
  | jq '.components.schemas.Payload.properties.journal'
{
  "type": "object",
  "required": [ "lines" ],
  "properties": {
    "unit":           { "type": "string" },
    "lines":          { "type": "integer" },
    "since":          { "type": "string" },
    "until":          { "type": "string" },
    "boot_id":        { "type": "string" },
    "max_priority":   { "type": "integer" },
    "after_cursor":   { "type": "string" },
    "follow_seconds": { "type": "integer" }
  }
}

Czyta się to jako payload odczytu journala: lines jest wymagane, unit nie — odczyt journala bez unitu czyta cały journal, i to jest sensowna rzecz do zamówienia. Żeby wypisać wszystkie grupy:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/openapi.json" \
  | jq -r '.components.schemas.Payload.properties | keys[]'

Którą grupę czyta dana operacja, jest w katalogu, w kolumnie Payload każdego wpisu. GET /api/v1/actions odpowiada na resztę tego, czym operacja jest — uprawnienie, ryzyko, timeout, czy nadaje się do kampanii, co ją weryfikuje:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/actions" \
  | jq '.items[] | select(.action == "journal.read")'
{
  "action": "journal.read",
  "mutating": false,
  "required_capability": "journald",
  "permission": "journal.read",
  "default_timeout_seconds": 60,
  "risk": "low",
  "campaign_mode": "none",
  "campaign_ready": false,
  "campaign_refusal": "this operation is not available for campaigns; run it host by host",
  "offline_policy": "skip_if_offline",
  "fanout_limit": 20,
  "cancel_mode": "safe",
  "retry_class": "automatic",
  "rollback": "none",
  "verification": "none",
  "resource_claims": [ { "class": "logs-read", "mode": "shared", "weight": 1 } ]
}

Cztery odmowy i co każda znaczy

Każda odmowa to obiekt problemu ze stabilnym code dla programów i detail dla ludzi. Te cztery spotyka pierwsza integracja, w kolejności, w jakiej zwykle je spotyka.

Operacja nie istnieje. Literówka w akcji, odpowiedź z całym słownikiem:

{
  "code": "unknown_action",
  "detail": "unknown operation type; allowed: agent.upgrade, backup.plan, backup.restore, ...",
  "status": 400
}

Payload jest poprawnym JSON-em o złym kształcie. Pola poszły bez opakowania — {"unit": "cron.service"} zamiast {"unit": {"unit": "cron.service"}}:

{
  "code": "invalid_payload",
  "detail": "the payload field \"unit\" takes opspec.UnitPayload and the order gave string; the payload of an operation is grouped by name, as {\"unit\":{...}}, and the groups are in the OpenAPI document under components.schemas.Payload",
  "status": 400
}

Payload jest złą grupą albo go brak. Kształt jest w porządku, a operacja nie ma z niego pożytku:

{
  "code": "invalid_payload",
  "detail": "the operation unit.restart requires a unit payload",
  "status": 400
}

Ciało wcale nie jest JSON-em. Inny kod, i to celowo — ta odmowa dotyczy żądania, nie payloadu w jego środku:

{
  "code": "invalid_body",
  "detail": "the request body is not valid JSON",
  "status": 400
}

Każdy kod, jaki maszyneria może postawić na żądaniu albo zadaniu, jest w przewodniku błędów, a panel serwuje ten sam przewodnik pod GET /api/v1/errors — więc program może sprawdzić, co mu powiedziano, bez człowieka czytającego tę stronę.

Odczyt na wielu hostach naraz

Odczyt, i tylko odczyt, można rozesłać po selektorze zamiast po hoście: POST /api/v1/reads. Zmiana nigdy nim nie jest.

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
        "action": "journal.read",
        "selector": { "environment": "test" },
        "payload": { "journal": { "unit": "cron.service", "lines": 2 } }
      }' \
  "$PANEL/api/v1/reads"
{
  "id": "baf39e0f-2057-44d2-8c8d-e83f8237f08a",
  "action": "journal.read",
  "host_count": 6,
  "counts": { "queued": 6, "running": 0, "succeeded": 0, "failed": 0 },
  "total_hosts": 6,
  "evaluated_hosts": 0,
  "unknown_hosts": 6,
  "partial": false,
  "unknown_reasons": { "not_finished": 6 },
  "kind": "timeline",
  "hosts": [
    { "job_id": "8b21e054-21e1-456c-bfc9-e34501b3de1c", "hostname": "agent-arch", "state": "queued" }
  ]
}

Jedno zadanie na host, każde do odczytania osobno pod /api/v1/jobs/{id}, i podsumowanie, które liczy to, co nadal nieznane, oraz dlaczego. unknown_hosts razem z unknown_reasons to zasada produktu w jednym polu: sześć hostów jeszcze nie odpowiedziało i jest to zaraportowane jako sześć nieznanych, a nie sześć zer. Zapytaj o ten sam identyfikator ponownie, żeby zobaczyć, jak się rozstrzygają. Rozsyłka jest ograniczona per operacja przez fanout_limit z katalogu akcji.

Kampania: podgląd, utworzenie, zatwierdzenie, anulowanie

Kampania to ta sama operacja na całej flocie, falami, z progami i weryfikacją per host. Zapytaj, czego dotknęłaby, przed utworzeniem:

curl -sS -H "Authorization: Bearer $TOKEN" \
  "$PANEL/api/v1/campaigns/preview?action=unit.restart&environment=test" | jq '{campaign_mode, count}'
{ "campaign_mode": "same_payload", "count": 8 }

Pełna odpowiedź niesie rozkład: jak dopasowane hosty rozkładają się po zdolnościach, środowiskach, lokalizacjach — i którym z nich brakuje zdolności, której operacja potrzebuje. Dwa hosty odpowiadające "reason": "unknown" pod capability to hosty, które nie zgłosiły, czy mają systemd, a kampania nie będzie za nie zgadywać.

Do utworzenia potrzebna jest nazwa, akcja i selektor; wszystko inne ma domyślną wartość, o której panel powie w zwróconym rekordzie:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
        "name": "restart cron on the test fleet",
        "action": "unit.restart",
        "selector": { "host_ids": ["42e2f7c7-8e02-4131-a797-55b5f0f53f54"] },
        "payload": { "unit": { "unit": "cron.service" } },
        "wave_size": 1,
        "failure_threshold_absolute": 1
      }' \
  "$PANEL/api/v1/campaigns"
{
  "id": "97e926ce-d57b-4798-bc61-e1b09bbe8b7d",
  "name": "restart cron on the test fleet",
  "action_type": "unit.restart",
  "state": "awaiting_approval",
  "revision": 1,
  "canary_size": 1,
  "wave_size": 1,
  "max_concurrent": 5,
  "requires_approval": true,
  "offline_policy": "wait_until_deadline",
  "reboot_policy": "never"
}

Startuje w awaiting_approval i nie robi nic, dopóki ktoś jej nie zatwierdzi:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{ "reason": "the monthly restart window" }' \
  "$PANEL/api/v1/campaigns/$CAMPAIGN/approve"

Zatwierdzenie może nieść payload_hash i wtedy jest odrzucane, jeśli plan zmienił się między odczytem a zatwierdzeniem. W środowisku wymienionym w FLOTESTRO_PRODUCTION_ENVIRONMENTS zatwierdzenie nie może przyjść od osoby, która zmianę zamówiła.

Dalej: /pause, /resume, /advance, /retry, /targets/{host}/skip i /cancel:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{ "reason": "called off, the window closed" }' \
  "$PANEL/api/v1/campaigns/$CAMPAIGN/cancel"

Własny revision kampanii rośnie przy każdej zmianie stanu i jest compare-and-set panelu: polecenie wydane kampanii, która w międzyczasie się ruszyła, dostaje 409 invalid_state, a nie wykonanie. Przeczytaj ponownie i zdecyduj ponownie.

Zapytać dwa razy, nie zrobić dwa razy

Sieci powtarzają żądania. Zamówienie, które tworzy pracę, przyjmuje Idempotency-Key, a powtórka pod tym samym kluczem zwraca zadanie już utworzone, nie drugie:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: nightly-cron-restart-2026-10-08' \
  -d '{ "action": "unit.restart", "payload": { "unit": { "unit": "cron.service" } } }' \
  "$PANEL/api/v1/hosts/$HOST/operations"

Klucz należy do wołającego: zrób go z tego, czym praca jest, a nie z momentu wysłania — inaczej ponowienie poniesie nowy klucz i zamówi pracę dwa razy. To samo pole może pójść w ciele jako idempotency_key; przy obu wygrywa nagłówek.

Zapis rekordu, który ktoś mógł ruszyć

Dwóch operatorów edytujących jeden rekord to zdarzenie zwyczajne, więc rekordy współdzielone noszą wersję. Odczyt odpowiada słabym znacznikiem encji:

curl -sS -D- -o /dev/null -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/hosts/$HOST"
HTTP/1.1 200 OK
Etag: W/"e62a8e5fd2181584"

Oddaj go przy zapisie i zapis wykona się tylko wtedy, gdy nic się w międzyczasie nie ruszyło:

curl -sS -X PUT -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'If-Match: W/"e62a8e5fd2181584"' \
  -d '{ "tags": ["database", "production"] }' \
  "$PANEL/api/v1/hosts/$HOST/tags"

Ze znacznikiem, który już nie jest aktualny:

{
  "code": "precondition_failed",
  "detail": "the record changed since it was read; read it again and repeat the write with its current ETag",
  "status": 412
}

Bez nagłówka zapis po prostu przechodzi, więc uważny klient zawsze go wysyła. Zwróć uwagę, czym jest to ciało tags: całą listą, nie zmianą w niej — tag pominięty to tag usunięty.

Odbiór śladu i sprawdzenie podpisu

Ustaw FLOTESTRO_WEBHOOK_URL i FLOTESTRO_WEBHOOK_SECRET, a panel będzie wysyłał ślad audytowy dalej, partiami, każdą podpisaną. Odbiornik sprawdzający samo ciało przyjąłby podrobione doręczenie: podpis obejmuje znacznik czasu, kropkę i ciało, i to właśnie nie pozwala przechwyconego doręczenia odtworzyć.

import hashlib, hmac

SECRET = b"the value of FLOTESTRO_WEBHOOK_SECRET"

def verify(headers, raw_body: bytes) -> bool:
    timestamp = headers.get("X-Flotestro-Timestamp", "")
    carried = headers.get("X-Flotestro-Signature", "").split("=")[-1].strip()
    if not timestamp or not carried:
        return False                      # bez podpisu albo podpis bez znacznika
    expected = hmac.new(SECRET, timestamp.encode() + b"." + raw_body,
                        hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, carried)

Każde doręczenie to partia zdarzeń śladu z identyfikatorami swoich końców, więc odbiornik pozna, czy ma dziurę:

{
  "first_id": 1402,
  "last_id": 1501,
  "events": [
    { "id": 1402, "aggregate_type": "campaign_target", "aggregate_id": "784bfdc7-b98c-418e-883f-...", "...": "..." }
  ]
}
