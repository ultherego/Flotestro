The HTTP API

Everything the panel does, a program can do. The API is the same surface the web panel runs on: 230 routes under /api/v1, answered in JSON, authorised by the same permissions and written to the same audit trail. This page is the route table as internal/adminapi/adminapi.go registers it and the conventions as internal/adminapi/openapi.go describes them; the panel serves its own OpenAPI document at GET /api/v1/openapi.json.

The shape of the interface

  • Reads use GET. Plans, operations and campaigns are created with POST and have explicit approve, cancel, pause and resume endpoints of their own.
  • Every list is paged on the server.
  • Errors are problem objects with a stable code.
  • The document describes itself: GET /api/v1/openapi.json is generated from the registered routes, so it can never drift from them.
  • The panel listens on FLOTESTRO_ADMIN_ADDR, 127.0.0.1:8080 by default, in plain HTTP; it is meant to sit behind a reverse proxy that terminates TLS.

Authentication

Two credentials reach the same permissions.

CredentialHow it travelsWho uses it
API tokenAuthorization: Bearer <token>Automation. A token belongs to a principal and carries that principal's permissions.
Browser sessionthe cookie flotestro_session, set after an OIDC loginA person in the panel.

The browser session takes precedence: when a request carries both, the cookie decides. The session cookie is HttpOnly, so a script in the browser cannot read it, and a state-changing request that authenticates with it has to confirm the caller's intent: the value of the readable cookie flotestro_csrf is sent back in the header X-Flotestro-CSRF. The cookie by itself authorises nothing. A request with no credential is anonymous, and an endpoint that needs one answers 401 with WWW-Authenticate: Bearer realm="flotestro" and the code unauthenticated.

Browser login is configured, not built in: without FLOTESTRO_OIDC_ISSUER the panel works on API tokens alone. A session is bounded by FLOTESTRO_SESSION_IDLE (8h by default) and by an absolute limit of 24 hours, and its groups are confirmed with the provider every FLOTESTRO_SESSION_GROUP_REFRESH (5m by default).

Step-up: the operations of the greatest impact

Some routes are not carried by a permission alone. A critical or destructive operation, a change to the access rules and a change in the directory require, beside the permission:

  • A reason, at least 8 characters, in the field reason of the body. Without it the answer is 400 reason_required - a refusal that signing in again will not fix.
  • Fresh authentication. The session's authentication must be no older than FLOTESTRO_STEPUP_MAX_AGE (5m by default) and, where FLOTESTRO_STEPUP_ACR is set, at that level. Otherwise the answer is 401 reauthentication_required, with required_max_age_seconds and authentication_age_seconds, or required_acr and session_acr, in the problem. A provider that reports no authentication time is refused the same way: an undetermined state cannot be read as “a moment ago”.
  • Permission for an API token to do it at all. FLOTESTRO_STEPUP_TOKENS is allow by default, and the token's order is recorded as authentication: api_token, reauthenticated: false. Set to refuse, a token is answered 401 reauthentication_required: an automaton cannot re-authenticate, because there is no human behind it.

What the panel accepted is recorded with the change itself, as the provider reported it: the purpose the operator typed, the authentication method (acr, amr) and the moment of authentication. The panel does not translate that into its own “mfa: yes”.

In a production environment - one named by FLOTESTRO_PRODUCTION_ENVIRONMENTS, prod,production by default - an approval may not be given by the person who ordered the change.

The shape of a refusal

Every refusal is the same object, served as application/problem+json:

{
  "type":   "about:blank",
  "title":  "Unprocessable Entity",
  "status": 422,
  "code":   "metrics_retention_too_short",
  "detail": "the raw retention 1h is shorter than the raw query window 24h plus the maximum lateness 24h; raise the retention or lower the window or the lateness"
}

The code is stable and meant for programs; the detail is for people. Every code the machinery can put on a task or a request is in the error guide, and the panel serves the same guide at GET /api/v1/errors.

Paging and cursors

Every list is paged on the server, by keyset rather than by offset: a page is fetched with limit and cursor, and the answer carries next_cursor, empty on the last page. The default page is 100 items and the ceiling is 500; a few lists say otherwise in their own table below. A cursor is an opaque token - the sort key of the last row, base64url without padding - so it is passed back exactly as it came; one this panel did not issue, or one issued under a different order, is refused rather than silently read as the first page.

A list that can be counted answers with items, count, next_cursor and total (how many match the filter across every page). The task list and the audit trail carry no total: they are browsed, not counted.

Sorting

A list that can be ordered takes sort as column or column:desc. An unknown column is refused with invalid_sort, and a cursor issued under one order is refused under another.

Revisions, ETag and If-Match

Two operators editing the same record is an ordinary event, so the records they share carry a version. A read of such a record answers with a weak entity tag in ETag; a write may carry it back in If-Match. Without the header the write proceeds; with it, a record that changed in between is refused with 412 precondition_failed and the current tag on the response: the record changed since it was read; read it again and repeat the write with its current ETag. If-Match: * matches any version.

A campaign carries a revision of its own, in the record rather than in a header: it grows with every state change, and a client that read the campaign at one revision and orders a transition at another is answered 409 concurrent_transition.

Some writes bind to what the operator saw in a different way again: an approval may carry payload_hash, and is refused when the plan changed between viewing and approving.

Idempotency keys

An order that creates work - a campaign, or an operation on a host - may carry Idempotency-Key. A repeat with the same key returns the resource already created instead of a second one. A caller that would rather put it in the body may: the header wins, and the body field is read when the header is absent.

Exports and streams

Twelve lists answer with a file as well as with JSON: format=csv gives one row per item, the same filters applied and the caller's own scope, with no page. The file is streamed as it is written - flushed every 500 rows - so a fleet-sized export reaches the browser rather than being built in memory first, and it is named after the list and the day (flotestro-hosts-2026-09-15.csv). A file stops at 50000 rows and its last row is marked truncated; one that broke off for a reason the list itself named is marked error, and an answer that describes only part of the fleet says so in the header X-Flotestro-Partial before the first row. A format that is neither json nor csv is refused with invalid_format rather than answered with JSON as if nothing had been asked.

The lists that carry a file: /api/v1/hosts, /api/v1/jobs, /api/v1/security, /api/v1/vulnerabilities, /api/v1/certificates, /api/v1/backups, /api/v1/policies/{id}/results, /api/v1/monitoring/alerts, /api/v1/campaigns/{id}/report, /api/v1/access/review, /api/v1/reports/{name}, /api/v1/notifications/deliveries.

The audit trail is exported differently, because it is evidence: GET /api/v1/audit/export streams the events between two moments as application/x-ndjson, oldest first, linked by a hash chain, with a closing line that carries the count and the digest of the last event. A failure midway cannot change the status code any more, so what the caller gets is a file without its closing line - which is exactly what the verifier reports as cut short.

A route ending in /events answers with text/event-stream: a stream of server-sent events, where a trail event carries an id so a reader that drops the connection resumes with Last-Event-ID.

Request identifiers

A caller may set X-Request-Id. The panel records it on every audit entry the request writes, so one identifier ties a change in an external system to the entry in the trail.
