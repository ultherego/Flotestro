## The clusters

Several rows are one decision, not one each. A fix applied to a cluster settles
every row in it, and a fix applied to one row of a cluster and not the others
leaves the product contradicting itself in a new place.

- **C1 - the relay buffer is described as memory.** Rows 6, 13, 17-prose, 18.
  One root cause: the documentation describes an in-memory buffer bounded by
  `buffer_max_bytes`, and the code has a disk spool whose limit is *derived*
  from that key. From `internal/relayconfig/config.go`: a file naming neither
  key gets 256 MiB (`fillDefaults` fills `buffer_max_bytes` with
  `DefaultBuffer`, then `fillSpoolDefaults` copies it); `buffer_max_bytes: 0`
  gets 1 GiB, because zero is not `> 0` and the fallback is
  `DefaultSpoolMaxBytes`; and `spool.max_bytes` may be set as far as
  `MaxSpoolBytes`, 64 GiB, which no runbook mentions. Whoever fixes one number
  has to fix the model behind all four.
- **C2 - `run` on the control plane starts what the control plane depends on.**
  Rows 1 (fixed in `1e6354a`) and 27i. `control-plane` carries
  `depends_on: migrate (service_completed_successfully)`, so
  `docker compose run --rm control-plane <anything>` runs the migration first.
  The read-only pre-flight and the deliberate migration step are the same
  mistake seen from two sides, and 27i adds a second half: the migrator
  credentials are declared on the `migrate` service only, so the command also
  runs with the wrong login.
- **C3 - the key-encryption-key runbook cannot be run as printed.** Rows 3, 4,
  27b, 27h. Four separate mechanisms in one document: a read-only container, a
  flag order, a container that does not hold the binary, and a key the panel
  reads from a variable the table says does not exist. One document, one review
  pass, one decision.
- **C4 - the external-database deployment cannot be brought up from its own
  example.** Rows 14, 15. A DSN naming a login `db/roles.sql` never creates, a
  `-f db/roles.sql` relative path that does not resolve where the procedure
  stands, and a header giving the same command for two different deployments.
  `APPROVER.md` §14 makes both PostgreSQL paths a release condition, so this is
  one path, not two typos.
- **C5 - the error reference's failure axis.** Rows 21, 23, 24. The page
  promises that every entry says whether it counts as a failure; two entries say
  the opposite of the code, one says nothing, and three use a CSS class the
  stylesheet does not define. Same axis, same page, one pass.
- **C6 - counts the registry outgrew.** Row 19. Five numbers transcribed from a
  registry that has since grown. One cause: the numbers are written by hand
  where the registry could produce them.

## `required-0.62`

Fixed before the release candidate. Each row names the `APPROVER.md` §14
criterion it meets.

### Row 2 - the air-gap procedure verifies a signature that does not exist

`docs/site/docs/installation.html:757-768`, its Polish twin, and
`docker/README.md:656-665` run `cosign verify` over four images. Only three are
signed: `.github/workflows/images.yml` builds `control-plane`, `relay` and
`admin-tools` under `id-token: write`, while `flotestro-package-repository` is
built by `release.yml`'s `repository-image` job, which declares
`contents: read` and `packages: write` and no `id-token`, and where
`grep -c cosign` returns 0. The loop carries no `set -e`, so the failed
iteration falls through to `docker pull` and `docker save`, and the unverified
image crosses the gap as if it had been checked. It is the isolated site's only
package source: every agent on that site is installed from it.

**P0: an unsigned stable release, and publication.** A verification step that
cannot fail is not a verification step.

### Row 3 - the key-encryption-key rotation cannot write the backup it takes (C3)

`docs/runbooks/key-encryption-key.md:152-155` runs
`podman exec ... crypto rewrap-kek --backup-to /var/backups/flotestro` inside a
container that `docker/compose.yaml:277` declares `read_only: true`, whose only
tmpfs is `/tmp` (`:279`) and whose only writable mount is the state volume
(`:243`). `internal/app/crypto_cmd.go:196` does `os.MkdirAll` on that path, which
is EROFS, and `:110-117` refuses a backup directory inside the state directory,
so there is no path that satisfies both. The `--dry-run` form returns at `:418`,
before `writeBackup` at `:429`: the rehearsal passes and the real run fails.

**P1: the officially supported path, and recovery.** The divergence between the
rehearsal and the real run is the defect, not the refusal.

### Row 5 - the relay procedure's two commands both abort before they start

`docs/site/docs/installation.html:708-715` lists the files to create and then
gives two commands. `docker/compose.relay.yaml:12` and `:72` both require
`${FLOTESTRO_RELAY_IMAGE:?...}`, and that variable appears nowhere under
`docs/` - `grep -rn FLOTESTRO_RELAY_IMAGE docs/` returns nothing. The enroll
service at `:97-100` also requires `./secrets/relay-enrollment-token`, which the
file list omits, so even with the image set the first command fails on a missing
secret.

**P1: the officially supported path.** `APPROVER.md` §8 and the final definition
both require the relay to have actually carried traffic, and this is the
procedure that brings it up.

### Row 6 - `0` is documented as "buffers nothing" and produces four times the default (C1)

`docs/runbooks/relay-disk-full.md:144` says "`0` buffers nothing", and
`docs/site/docs/configuration.html:458` with its Polish twin `:453` say "Zero
means do not buffer: the results from the outage are then lost deliberately".
`internal/relayconfig/config.go:199-205` takes `buffer_max_bytes` only when it
is `> 0`; zero falls through to `DefaultSpoolMaxBytes`, 1 GiB, which is four
times the 256 MiB an unset file gets. An operator who sets `0` to stop buffering
gets the largest spool the defaults can produce.

**P1: correctness of operations, and durability.** The setting does the opposite
of what the reference says, on the one value an operator reaches for
deliberately.

### Row 7 - the relay reboot advice shadows the unit the rollback restarts

`docker/README.md:1363-1367` says the relay does not come back after a reboot
under rootless Podman and tells the operator to hand-write
`/etc/systemd/system/flotestro-relay.service`. It does come back:
`docker/compose.relay.yaml:15-18` sets `restart: always` precisely so the unit
rootless Podman ships replays it, `docker/host-setup.sh:35` checks for
`unless-stopped` for the same reason, and `docker/README.md:120-140` documents
the mechanism. The hand-written unit takes the path the relay package's own unit
occupies, and `docker/README.md:1395` - "going back is stopping the containers
and starting the unit" - restarts exactly that unit. The instruction breaks the
documented way back. It was true until `ce5bd53` and `0f575ad` (2026-09-29).

**P1: the officially supported path, and recovery.** The advice was correct once
and now removes the rollback it points at.

### Row 9 - the metrics runbook's route does not exist

`docs/runbooks/metrics-gap.md:46` and `:118` both use
`GET /api/v1/fleet/monitoring`. `internal/adminapi/monitoring.go:28` registers
`GET /api/v1/monitoring`, and the whole family under `:31-41` is unprefixed.
The route never existed, so the runbook's two readings of `hosts_reporting`
against `hosts_silent` - the step that tells the operator whether the gap is

**P1: recovery.** A recovery runbook whose diagnostic call 404s does not
recover anything.

### Row 10 - the metrics runbook prescribes a setting a stored value overrides

`docs/runbooks/metrics-gap.md:84-88` tells the operator to raise
`FLOTESTRO_METRICS_MAX_LATENESS` and `FLOTESTRO_METRICS_RETENTION_RAW`
together. `internal/app/app.go:219-222` states that these are the initial values

source is in force. On any installation that has ever stored its monitoring
settings, the prescribed change restarts the panel and does nothing.

**P1: recovery, and a silent success after a failure.** The operator is told the
window has been widened when it has not been.

### Row 11 - the restore commands name files nothing produces, and untar into `/`

`docs/runbooks/db-restore.md:181` restores the state directory with
`tar -C / -xzf flotestro-state-<stamp>.tgz` and `:183` restores the database
from `flotestro-<stamp>.dump`. Neither name is produced by anything: the backup
writes `./backups/<id>/database.dump` and `state.tar.zst`, as the same file says
at `:168-171`. `-z` is gzip over a zstd archive, so the command fails; `tar -C /`
would scatter the state-relative paths of the archive across `/` if it did not.
The procedure never uses the shipped `admin-restore restore <id>` path that
`docker/compose.yaml` declares and that the file's own backup step is the pair
of.

**P1: recovery, and durability.** `APPROVER.md` §10 and the final definition
make a restore that has actually been carried out a release condition; this is
the document it would be carried out from.

### Row 13 - three places say the relay buffers in memory (C1)

### Row 4 - `forget-files --dry-run` is refused before it prints (C3)

`docs/runbooks/key-encryption-key.md:208` prints
`crypto forget-files --dry-run --backup-to ...` with neither

already tells the operator where to read both from

text itself. Unlike row 3 there is no divergence between the rehearsal and the
real run: both refuse the same way, and neither changes anything.

## `documented-limit`

Real, and the documentation will state it as a limitation rather than deny it.

### Row 22 - some error meanings are editorial, not quoted

`docs/site/docs/errors.html:123` says the meaning and the action are quoted
exactly as the panel shows them. Six entries were rewritten by hand:
`idempotency_key_reused`, `cancel_ack_stale`, `inhibitors_unknown`,
`unsafe_restore_target`, `crypto_state_stale` and `migration_checksum_mismatch`.
The page will say that the wording is edited for reading where the panel's own
text is terse, and that the panel is the authority on the exact string.

### Row 27c - `env.example` lists the keys an installation changes, not all of them

`docs/site/docs/installation.html:193-194` and `docker/compose.yaml:11` say
`env.example` lists every setting. The file carries 16 keys; the control plane
reads 98 distinct `FLOTESTRO_*` variables through `config.Env*` and more through
its flags. The promise becomes: the file lists the keys a deployment normally
changes and names the ones an installation for real hosts has to, and
`configuration.html` is the full reference.

### Row 27d - not every setting has a flag

`docs/site/docs/configuration.html:123` says every setting of a Flotestro binary
is an environment variable with a command-line flag of the same meaning that
overrides it. There are 35 flags and several families have none. The page will
say that the environment variable is the interface and that a flag exists where
one is useful.

### Row 27f - five variables have a `_FILE` form, not every variable

`docker/README.md:442` says every variable has a `_FILE` form.
The code recognises `FLOTESTRO_CA_FILE`, `FLOTESTRO_KEK_FILE`,
`FLOTESTRO_KEK_NEXT_FILE`, `FLOTESTRO_SECRETS_KEY_FILE`,
`FLOTESTRO_RELEASE_MANIFEST_FILE` and, on the agent side,
`FLOTESTRO_HELPER_PIN_FILE` and `FLOTESTRO_HELPER_HOST_ID_FILE`; the DSN and the
PostgreSQL password are handled separately. The section will say that every
variable *that carries a secret* has a `_FILE` form, which is the promise the
section is actually about.

## `deferred`

A later release. Each row names an owner, a ticket, a deadline and the condition
that pulls it forward. Where those are the owner's to set, they stand as
explicit TODOs rather than invented values.

### Row 8 - "none of them contains another", about roles

`docs/site/docs/roles.html:126` says the permission lists of the roles overlap
but none contains another. From `internal/authz/model.go:373-560`: viewer 31,
auditor 23, operator 63, approver 12, identity_admin 24, platform_admin 187 -
every one of the five is a strict subset of `platform_admin`, and the same page
says so at `:282`.

**Impact:** a reader could conclude that least-privilege assignment needs roles
stacked, when one role already contains another's list.

**Compensating control:** `:282` states the containment plainly on the same
page, and `GET /api/v1/roles` serves the permission list role by role.
