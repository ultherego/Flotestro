11. Worked examples

The reference pages say what every route and every operation is. This page is the other half: calls you can paste into a terminal, and what came back when they were run. Every request and every response below was run against a real installation; the identifiers are from that run, so yours will differ.

What you need: an address and a token

The panel answers on FLOTESTRO_ADMIN_ADDR, 127.0.0.1:8080 by default, in plain HTTP behind whatever terminates TLS for it. Nothing below needs a browser.

A fresh installation writes one token into its state directory, as bootstrap-token. In the container deployment that directory is a volume, so the file is read out of it rather than off the host:

docker compose exec -T control-plane cat /var/lib/flotestro/bootstrap-token

That token belongs to a principal called bootstrap-admin and lives 30 days. It is the credential that creates the others: a long-lived automation should have a token of its own, issued to its own principal with its own permissions, through POST /api/v1/principals/{id}/tokens. Keep the address and the token in the shell for the rest of this page:

PANEL=http://127.0.0.1:8080
TOKEN=$(docker compose exec -T control-plane cat /var/lib/flotestro/bootstrap-token)

A token is not a session

Both credentials reach the same permissions, but a browser session is bounded, carries a CSRF header and can be re-authenticated; a token cannot. That matters for the few operations that demand fresh authentication, and FLOTESTRO_STEPUP_TOKENS=refuse is how an installation says a token may never order them. See step-up.

The first call, and the shape of a list

Two hosts, sorted by name:

curl -sS -H "Authorization: Bearer $TOKEN" \
  "$PANEL/api/v1/hosts?limit=2&sort=hostname"

Every list has the same envelope. count is this page, total is how many match the filter across every page, and next_cursor is empty on the last page:

{
  "count": 2,
  "total": 8,
  "next_cursor": "AgAAAAMAAAAIaG9zdG5hbWUAAAAMYWdlbnQtZGViaWFu...",
  "items": [
    {
      "id": "91010c96-a7ed-4733-91ee-0f06cc7a6482",
      "hostname": "agent-arch",
      "site": "lab",
      "environment": "test",
      "lifecycle_state": "active",
      "os_family": "arch",
      "agent_version": "0.62.0",
      "connection_state": "online",
      "last_seen_at": "2026-10-08T09:40:28.018922Z",
      "agent_build_commit": "7bc2abf369a275d51ed01effafb66be8f28f6594",
      "helper_capability_mode": "enforce",
      "failed_units": 0,
      "pending_updates": 12,
      "pending_security_updates": null,
      "management_address": "192.168.56.70"
    }
  ]
}

A host record carries 35 fields; the ones above are the ones a list is usually read for. Note pending_security_updates: null, not 0. The host has not reported that number, and the panel does not invent one — which is why a sort puts an unknown count below zero rather than among the zeroes.

Walking a list to the end

A cursor is opaque: the sort key of the last row, passed back exactly as it came. It is not an offset, so rows inserted while you page do not shift the window or repeat a row:

cursor=
while :; do
  page=$(curl -sS -H "Authorization: Bearer $TOKEN" \
    "$PANEL/api/v1/hosts?limit=100&sort=hostname&cursor=$cursor")
  echo "$page" | jq -r '.items[].hostname'
  cursor=$(echo "$page" | jq -r '.next_cursor // empty')
  [ -n "$cursor" ] || break
done

A cursor this panel did not issue, or one issued under a different sort, is refused — it is not quietly read as the first page.

Ordering one operation on one host

This is the call most automation is written around, and it has two details worth getting right the first time.

The route is per host. An operation is created under the host it acts on: POST /api/v1/hosts/{id}/operations. There is no route that takes a host identifier in the body.

The field is action going in and action_type coming back. The request names the operation in action; the job record that comes back reports it as action_type, because a job has a type and a version. A request that sends action_type is a request with no action in it.

Restarting a service on one host:

HOST=42e2f7c7-8e02-4131-a797-55b5f0f53f54

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: restart-cron-$(date +%s)" \
  -d '{
        "action": "unit.restart",
        "payload": { "unit": { "unit": "cron.service" } }
      }' \
  "$PANEL/api/v1/hosts/$HOST/operations"

201 Created, and the job as the panel recorded it:

{
  "id": "904dfe79-8c6c-4b3f-9fc1-ee7638ff5b6f",
  "host_id": "42e2f7c7-8e02-4131-a797-55b5f0f53f54",
  "hostname": "agent-debian",
  "action_type": "unit.restart",
  "action_version": 1,
  "payload": { "unit": { "unit": "cron.service" } },
  "payload_hash": "17af2e027304d8f9737c4e1551b65e3a8ac219f241f1e3eb14b6b4b70bf961f1",
  "state": "queued",
  "requires_approval": false,
  "required_approvals": 1,
  "collected_approvals": 0,
  "preconditions": {
    "os_family": "debian",
    "required_capabilities": [ "systemd" ]
  },
  "timeout_seconds": 120
}

The payload sits inside a named group — "unit": { ... } — and that group is the same for every operation that acts on a unit. preconditions is the panel telling you what it will hold the host to before the work is dispatched; a host that does not meet them is refused rather than attempted.

Some operations will not start on a request alone

An operation of high or critical risk may need reason (at least 8 characters), the hostname typed back in target_confirmation, an approval by somebody else, or authentication no older than a few minutes. Which of those applies is in the operations reference per operation, and the refusal always says which one is missing.

Reading what the host did

The job record carries the state; the attempt carries what the host said. Ask for the job first:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/jobs/$JOB" | jq '{state, finished_at, result_status}'
{
  "state": "succeeded",
  "finished_at": "2026-10-08T09:42:12.636754Z",
  "result_status": "succeeded"
}

Then the attempts, which is where the output, the exit code and the identity of the gateway that dispatched it are:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/jobs/$JOB/attempts" | jq '.items[0]'
{
  "attempt_number": 1,
  "status": "succeeded",
  "exit_code": 0,
  "gateway_id": "cp-01",
  "session_id": "1353c457-2ae1-4391-b445-5c0b11091da1",
  "dispatched_at": "2026-10-08T09:42:12.440228Z",
  "started_at": "2026-10-08T09:42:12.446875Z",
  "finished_at": "2026-10-08T09:42:12.636754Z",
  "output_truncated": false,
  "replayed": false,
  "stdout": "2026-10-08T08:17:01+00:00 agent-debian CRON[2351]: pam_unix(cron:session): session closed for user root\n..."
}

There is one record per attempt, so a retry does not overwrite what the first one said. replayed marks an answer the panel took from the host's own record of a request it had already carried out, rather than a second execution. output_truncated tells you the output hit max_output_bytes — ask for more with that field on the order if you need it.

A job that ran but could not be confirmed is not reported as a success: result_status becomes applied_unverified, which means the change was made and the verifier could not read the host back. It is a state to watch for, not an error to retry blindly.

Where the payload shape comes from

A payload is grouped by name. There are 43 groups, one per kind of thing an operation acts on, and an operation reads exactly one of them. The groups and their fields are in the document the panel generates from its own routes, so they cannot drift from the code:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/openapi.json" \
  | jq '.components.schemas.Payload.properties.journal'
{
  "type": "object",
  "required": [ "lines" ],
  "properties": {
    "unit":           { "type": "string" },
    "lines":          { "type": "integer" },
    "since":          { "type": "string" },
    "until":          { "type": "string" },
    "boot_id":        { "type": "string" },
    "max_priority":   { "type": "integer" },
    "after_cursor":   { "type": "string" },
    "follow_seconds": { "type": "integer" }
  }
}

Read it as the payload of a journal read: lines is required, unit is not — a journal read with no unit reads the whole journal, which is a legitimate thing to ask for. To list every group:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/openapi.json" \
  | jq -r '.components.schemas.Payload.properties | keys[]'

Which group an operation reads is in the catalogue, in the Payload column of every entry. GET /api/v1/actions answers the rest of what an operation is — its permission, its risk, its timeout, whether a campaign can run it, what verifies it:

curl -sS -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/actions" \
  | jq '.items[] | select(.action == "journal.read")'
{
  "action": "journal.read",
  "mutating": false,
  "required_capability": "journald",
  "permission": "journal.read",
  "default_timeout_seconds": 60,
  "risk": "low",
  "campaign_mode": "none",
  "campaign_ready": false,
  "campaign_refusal": "this operation is not available for campaigns; run it host by host",
  "offline_policy": "skip_if_offline",
  "fanout_limit": 20,
  "cancel_mode": "safe",
  "retry_class": "automatic",
  "rollback": "none",
  "verification": "none",
  "resource_claims": [ { "class": "logs-read", "mode": "shared", "weight": 1 } ]
}

Four refusals, and what each one means

Every refusal is a problem object with a stable code for programs and a detail for people. These four are the ones a first integration meets, in the order it usually meets them.

The operation does not exist. A typo in the action, answered with the whole vocabulary:

{
  "code": "unknown_action",
  "detail": "unknown operation type; allowed: agent.upgrade, backup.plan, backup.restore, ...",
  "status": 400
}

The payload is valid JSON of the wrong shape. The fields were sent unwrapped — {"unit": "cron.service"} instead of {"unit": {"unit": "cron.service"}}:

{
  "code": "invalid_payload",
  "detail": "the payload field \"unit\" takes opspec.UnitPayload and the order gave string; the payload of an operation is grouped by name, as {\"unit\":{...}}, and the groups are in the OpenAPI document under components.schemas.Payload",
  "status": 400
}

The payload is the wrong group, or missing. The shape is fine and the operation cannot use it:

{
  "code": "invalid_payload",
  "detail": "the operation unit.restart requires a unit payload",
  "status": 400
}

The body is not JSON at all. A different code, on purpose — this one is about the request, not about the payload inside it:

{
  "code": "invalid_body",
  "detail": "the request body is not valid JSON",
  "status": 400
}

Every code the machinery can put on a request or a task is in the errors guide, and the panel serves the same guide at GET /api/v1/errors — so a program can look up what it was told without a human reading this page.

A read across many hosts at once

A read, and only a read, can be fanned out over a selector instead of a host: POST /api/v1/reads. A change is never one of them.

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
        "action": "journal.read",
        "selector": { "environment": "test" },
        "payload": { "journal": { "unit": "cron.service", "lines": 2 } }
      }' \
  "$PANEL/api/v1/reads"
{
  "id": "baf39e0f-2057-44d2-8c8d-e83f8237f08a",
  "action": "journal.read",
  "host_count": 6,
  "counts": { "queued": 6, "running": 0, "succeeded": 0, "failed": 0 },
  "total_hosts": 6,
  "evaluated_hosts": 0,
  "unknown_hosts": 6,
  "partial": false,
  "unknown_reasons": { "not_finished": 6 },
  "kind": "timeline",
  "hosts": [
    { "job_id": "8b21e054-21e1-456c-bfc9-e34501b3de1c", "hostname": "agent-arch", "state": "queued" }
  ]
}

One job per host, each readable on its own at /api/v1/jobs/{id}, and a summary that counts what is still unknown and why. unknown_hosts with unknown_reasons is the rule of the product in one field: six hosts have not answered yet, and that is reported as six unknowns rather than six zeroes. Ask the same identifier again to see them resolve. A fan-out is capped per operation by fanout_limit from the action catalogue.

A campaign: preview, create, approve, cancel

A campaign is the same operation across a fleet, in waves, with thresholds and a verification per host. Ask what it would touch before creating it:

curl -sS -H "Authorization: Bearer $TOKEN" \
  "$PANEL/api/v1/campaigns/preview?action=unit.restart&environment=test" | jq '{campaign_mode, count}'
{ "campaign_mode": "same_payload", "count": 8 }

The full answer carries a distribution: how the matched hosts break down by capability, by environment, by site — and which of them lack the capability the operation needs. Two hosts answering "reason": "unknown" under capability are hosts that have not reported whether they have systemd, and the campaign will not guess on their behalf.

Creating one needs a name, an action and a selector; everything else has a default the panel will tell you about in the record it returns:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
        "name": "restart cron on the test fleet",
        "action": "unit.restart",
        "selector": { "host_ids": ["42e2f7c7-8e02-4131-a797-55b5f0f53f54"] },
        "payload": { "unit": { "unit": "cron.service" } },
        "wave_size": 1,
        "failure_threshold_absolute": 1
      }' \
  "$PANEL/api/v1/campaigns"
{
  "id": "97e926ce-d57b-4798-bc61-e1b09bbe8b7d",
  "name": "restart cron on the test fleet",
  "action_type": "unit.restart",
  "state": "awaiting_approval",
  "revision": 1,
  "canary_size": 1,
  "wave_size": 1,
  "max_concurrent": 5,
  "requires_approval": true,
  "offline_policy": "wait_until_deadline",
  "reboot_policy": "never"
}

It starts in awaiting_approval and does nothing until somebody approves it:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{ "reason": "the monthly restart window" }' \
  "$PANEL/api/v1/campaigns/$CAMPAIGN/approve"

An approval may carry payload_hash, and is then refused if the plan changed between being read and being approved. In an environment named by FLOTESTRO_PRODUCTION_ENVIRONMENTS the approval may not come from the person who ordered it.

From there: /pause, /resume, /advance, /retry, /targets/{host}/skip, and /cancel:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{ "reason": "called off, the window closed" }' \
  "$PANEL/api/v1/campaigns/$CAMPAIGN/cancel"

The campaign's own revision grows with every state change and is the panel's compare-and-set: an order given against a campaign that moved in between is answered 409 invalid_state rather than applied. Read it again and decide again.

Asking twice without doing it twice

Networks repeat requests. An order that creates work takes Idempotency-Key, and a repeat under the same key returns the job that was already created instead of a second one:

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: nightly-cron-restart-2026-10-08' \
  -d '{ "action": "unit.restart", "payload": { "unit": { "unit": "cron.service" } } }' \
  "$PANEL/api/v1/hosts/$HOST/operations"

The key belongs to the caller: make it from what the work is, not from the moment it was sent, or a retry will carry a new key and order the work twice. The same field may go in the body as idempotency_key; the header wins when both are present.

Writing a record somebody else may have moved

Two operators editing one record is an ordinary event, so the shared records carry a version. A read answers with a weak entity tag:

curl -sS -D- -o /dev/null -H "Authorization: Bearer $TOKEN" "$PANEL/api/v1/hosts/$HOST"
HTTP/1.1 200 OK
Etag: W/"e62a8e5fd2181584"

Send it back on the write, and the write happens only if nothing moved in between:

curl -sS -X PUT -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'If-Match: W/"e62a8e5fd2181584"' \
  -d '{ "tags": ["database", "production"] }' \
  "$PANEL/api/v1/hosts/$HOST/tags"

With a tag that is no longer current:

{
  "code": "precondition_failed",
  "detail": "the record changed since it was read; read it again and repeat the write with its current ETag",
  "status": 412
}

Without the header the write simply proceeds, so a careful client always sends it. Note what that tags body is: the whole list, not a change to it — a tag left out is a tag removed.

Receiving the trail, and checking the signature

Set FLOTESTRO_WEBHOOK_URL and FLOTESTRO_WEBHOOK_SECRET and the panel posts the audit trail onward in batches, each one signed. A receiver that checks the body alone would accept a forged delivery: the signature covers the timestamp, a dot, and the body, which is what keeps a captured delivery from being replayed.

import hashlib, hmac

SECRET = b"the value of FLOTESTRO_WEBHOOK_SECRET"

def verify(headers, raw_body: bytes) -> bool:
    timestamp = headers.get("X-Flotestro-Timestamp", "")
    carried = headers.get("X-Flotestro-Signature", "").split("=")[-1].strip()
    if not timestamp or not carried:
        return False                      # unsigned, or signing nothing replayable
    expected = hmac.new(SECRET, timestamp.encode() + b"." + raw_body,
                        hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, carried)

Each delivery is a batch of trail events with the identifiers of its ends, so a receiver can tell whether it has a gap:

{
  "first_id": 1402,
  "last_id": 1501,
  "events": [
    { "id": 1402, "aggregate_type": "campaign_target", "aggregate_id": "784bfdc7-b98c-418e-883f-...", "...": "..." }
  ]
}

Answer 2xx and the panel moves its cursor; answer anything else, or nothing, and it keeps the place and tries again. The consumer never moves past an event it did not deliver, which is why a receiver that is down loses nothing.
