2. Architecture

An installation has five parts: the control plane, an unprivileged agent on every host, a root helper beside it, a relay for a site that cannot reach the panel directly, and PostgreSQL. Each one proves an identity to the next, and each one has a state that is not the other's backup.

The gateway and the enrollment ports are end to end

8443 and 8444 are reached by the fleet directly and their TLS must not be terminated by an HTTP proxy: the gateway authenticates the host by its client certificate, and a proxy that terminates the session takes that away. Only 8080 goes behind a reverse proxy. The names in FLOTESTRO_ADVERTISE enter the gateway's certificate, so they have to be the names the fleet really reaches - never a Compose service name.

The control plane

One binary. Inside it, the pieces that matter to an operator are:

API and panel
The REST API under /api/v1 and the built panel served from FLOTESTRO_WEB_ROOT; an empty web root serves the API alone. Every response carries a strict content security policy, and the panel is never framed.
Agent gateway
Holds one stream per connected host, delivers task envelopes, takes results, inventory reports and samples, issues the capabilities the helper verifies, and hands out secrets under a lease. Dispatch is rate-limited by FLOTESTRO_DISPATCH_RATE, 100 envelopes a second by default.
Enrollment
Spends one-time tokens, which are stored as digests, and issues a host or relay certificate from a key that never leaves the machine.
PKI
The fleet CA lives in the state directory as ca.pem and ca.key, with ca-pending.* and ca-retired/<serial>.pem during a rotation. Agent certificates last FLOTESTRO_AGENT_CERT_TTL, 720 hours by default, and the agent renews after two thirds of that.
Scheduler and campaign engine
Turns approved work into leased tasks, holds the waves of a campaign, claims capacity from the budgets and settles what came back.
Monitoring
Stores the raw samples in one table partition per day, recomputes the quarter-hour rollups that are marked dirty, and evaluates the alert rules - on exactly one instance at a time, under a lease of FLOTESTRO_METRICS_EVALUATOR_LEASE, 45 seconds by default.
Notifications
A durable outbox: events are posted to the webhook in batches, signed with HMAC-SHA256, delivered at least once and in order, with a cursor per consumer.
Housekeeping
One sweep an hour, five thousand rows of a kind at a time, against the retentions. Ended agent sessions are swept after thirty days whatever the settings say.

More than one instance

Several control planes may run against one database. Each one has its own FLOTESTRO_GATEWAY_ID - sessions and leases are tagged with it, and a second instance claiming an identity that is already held refuses to start with gateway_id_in_use.

A host is connected to exactly one instance, and an operator's request lands on whichever instance answered the browser. Most decisions are rows and travel by themselves. The work that needs the host's open stream - the final task of a decommission, ending a session at a quarantine or an identity recovery - is written as an order in gateway_commands, addressed to the session that owned the host at the moment of the decision and to the fencing token of that claim. Ownership is a lease of 45 seconds renewed every 15; a write from an instance whose claim was superseded is refused by the database itself as session_fence_stale, and the task simply goes back to the queue.

The order loop is woken by the trail, so an order normally reaches its owner within a round trip; FLOTESTRO_COMMAND_POLL (5s) is the floor under that and FLOTESTRO_COMMAND_EXPIRY (5m) is how long an unclaimed order stands before it is settled as expired with nothing done. The request that gave the order waits up to 60 seconds; a decommission not finished by then answers with the phase handover_pending and the host stands in retiring while its owner finishes the handshake. An installation with one instance never writes an order at all.

The agent

The agent runs as an unprivileged user and holds one stream to the gateway. It reads the host, it never decides anything about it, and it cannot change anything by itself: every change goes through the helper.

Its state directory, /var/lib/flotestro-agent (FLOTESTRO_AGENT_STATE_DIR), holds:

  • identity/current, a symlink to identity/generations/<serial>/ with agent.key, agent.pem and trust-bundle.pem. A renewal writes a new generation and moves the link; the daemon starts only when identity/current/agent.pem exists, which is the ConditionPathExists in flotestro-agent.service.
  • metrics-spool, at most 240 small files: four hours of samples at one a minute. A sample is written before it is sent and deleted only when the panel answers that very sample; on reconnect the agent sends what was never answered, oldest first. Past the bound the oldest goes - a panel away for a week costs the host four hours of readings, not a week.
  • The idempotency journal of performed tasks, so a task delivered twice is done once.

The host itself is described by /etc/flotestro/agent.yaml: the enrollment URL, the gateway URLs, the CA file and the mode. The environment variables of /etc/flotestro/agent.env override the file and exist for an image or a test. Two settings are worth knowing before a fleet is rolled out: FLOTESTRO_MAX_CONCURRENT_TASKS (2) bounds what one host runs at once, and FLOTESTRO_AGENT_MODE chooses between full and read_only - a read-only agent reports and changes nothing.

Inventory is collected on a cadence rather than all at once: a base cycle of FLOTESTRO_INVENTORY_MINUTES, 15 minutes by default, with ±10 % jitter so that a fleet started by one reboot does not report in step for the rest of its life. See the inventory section for which module is read how often.

The daemon never enrolls. Enrollment is flotestro-agentctl enroll, run once by an operator; FLOTESTRO_ENROLLMENT_TOKEN in the daemon's environment is ignored and reported at every start until it is removed.

The root helper

The helper is the only part that runs as root, and it is deliberately small: a socket, a fixed repertoire of actions, and no network. It is socket-activated and exits after FLOTESTRO_HELPER_IDLE_SECONDS (300) of quiet; systemd starts it again on the next command. Its wire protocol is length-prefixed protobuf, version 1, with a frame limit of 4 MiB - the helper runs as root and must not let its peer allocate memory at will. An action it does not know is unknown_action; a unit it protects is protected_unit; a resource class already busy is locked.

Two checks stand in front of every request. The first is the kernel's: SO_PEERCRED has to name the uid of FLOTESTRO_AGENT_USER, and the check is made against the socket, not against anything in the message. The second is the panel's capability.

The capability

Every mutating request is meant to carry a capability the control plane signed with Ed25519 for exactly this host, task, action and payload. The helper verifies it against the root-owned keyring in FLOTESTRO_HELPER_TRUST_DIR (/etc/flotestro/helper-trust.d, one <key_id>.pub per key), against the host identifier in FLOTESTRO_HELPER_HOST_ID_FILE, and against the nonces it has already consumed under FLOTESTRO_HELPER_REPLAY_DIR. Because the keyring and the identity belong to root, a compromised agent cannot lower what they say.

FLOTESTRO_HELPER_CAPABILITY_MODEA request with no capabilityA request with a bad one

Reads never need a capability. Set enforce on a host once the panel's flotestro_helper_capability_total{outcome="legacy_agent"} stays at zero. The validity window is short and depends on the class of the action: 5 minutes by default, 10 for a package transaction, 2 for a destructive storage operation. The helper allows 30 seconds of clock skew, and refuses a longer window than its class permits with capability_ttl_too_long - a window the panel would not have signed. The other refusals are capability_wrong_host, capability_wrong_action, capability_expired, payload_hash_mismatch, payload_binding_mismatch, capability_unknown_key, capability_bad_signature, capability_invalid_nonce and capability_replay.

File versions

The helper also keeps what a managed file held before each write, under FLOTESTRO_HELPER_FILE_VERSION_DIR (/var/lib/flotestro-helper/files): one directory per file, named by the digest of its path, root's own, mode 0700, every copy 0600. It keeps FLOTESTRO_HELPER_FILE_VERSIONS copies of one file (10) inside FLOTESTRO_HELPER_FILE_VERSION_BYTES in total (32 MiB). A write that cannot make the copy refuses with file_version_not_kept rather than making a change nothing can undo, and file.rollback names one version by its checksum - a checksum this host never kept is file_version_unknown, not the newest copy.

The relay

A relay serves one site whose hosts cannot reach the panel directly. It terminates their sessions on :8453, forwards them upstream to one of upstream.gateway_urls, and spools what the centre has not acknowledged. It is configured by /etc/flotestro/relay.yaml alone - one variable, FLOTESTRO_ENROLLMENT_TOKEN, is read by the enroll command and by nothing else. flotestro-relay config show prints what the file resolves to.

Its site is an expectation, not a grant: the scope of a relay is what its enrollment token granted, and the token settles it. No relay may advertise a name that is in FLOTESTRO_ADVERTISE - those names are reserved.

On a restart the index is rebuilt from the segments, and a record damaged at the end of the last segment is cut off without touching the records before it. /healthz is liveness and stays 200 through an outage of the centre - a relay whose link is down is the one process that must not be restarted - while /readyz answers 503 with the reason: relay_upstream_unreachable, relay_spool_critical, relay_spool_unwritable, relay_certificate_expired or relay_certificate_unknown. Its body also carries safe_to_restart, true only when nothing waits in the spool.

Whose word the centre takes for a host

A session that arrives through a relay raises a question the direct one does not: is the host really the host, or is it the relay saying so? The answer is the host's own signed identity envelope (relay.identity v2), verified at the centre under every mode - relay, host, certificate by serial, site and environment, payload digest, signature and sequence - and a session that carries one is marked relay_identity: end_to_end. A bad envelope is refused under every mode with relay_envelope_invalid, relay_body_hash_mismatch, relay_sequence_replayed or relay_host_signature_invalid.

FLOTESTRO_RELAY_IDENTITY decides what happens without an envelope: observe and prefer (the default) let the session in on the relay's attestation or its word alone, recorded as attested or weak; enforce refuses a relay that names a host without an envelope with relay_identity_missing, and an agent too old to sign with blocked_upgrade_required. A renewal or a secret fetch through a relay requires the envelope under every mode. Upgrade the panel, then the relays, then the agents, and set enforce once weak and relay_only sessions are at zero.

The database and the state directory

PostgreSQL is the only source of truth. Hosts, certificates, jobs and their attempts, campaigns and their targets, budgets, encrypted secrets, the outbox and its cursor, the audit trail, the monitoring samples and rollups all live in the database named by FLOTESTRO_DATABASE_URL. The panel keeps the fleet's state nowhere else.

What is not in the database is the state directory, and that is the whole reason the two are one backup pair:

  • ca.pem, ca.key, and during a rotation ca-pending.pem, ca-pending.key, ca-pending.at and ca-retired/<serial>.pem - without ca.key no host can renew or enroll.
  • keys/<key-id>.key, the key encryption keys of the secret store - without the active one every row of the store is unreadable. A key held as a systemd credential (FLOTESTRO_SECRETS_KEY_CREDENTIAL) lives wherever the unit's LoadCredential= points, and that place is in the backup set instead.
  • The helper signing key, whose public half the hosts hold as the capability keyring.
  • bootstrap-token, on a first start only.

Never restore one half without the other

A database restored beside a different state directory is an installation that cannot talk to its own fleet. The control plane checks the state against the installation record at every start and stops, fail-closed, with the state named - installation_state_mismatch, secrets_key_unavailable, issuer_key_unavailable, pki_state_mismatch or crypto_state_ambiguous. It never creates a fresh CA in place of a missing one. Two instances must not run with separate state directories against one database.

Why the agent is a package and the control plane is an image

The agent manages the host itself: its PID 1, its devices, its package database, its real /proc. A container that could do all of that would be a --privileged container sharing every namespace - something with the word container in it and nothing isolated about it. So the agent and its helper are native packages, installed from the project's signed repository, upgraded by the host's own package manager or by the panel's agent.upgrade operation against a package it has verified.

The control plane has the opposite shape. It talks to a database and to the network, it owns no host, and it benefits from a runtime that gives it a read-only root filesystem, no capabilities and one writable volume. Its image is distroless: the binaries, the system certificate store and the built panel, with no shell, no package manager, no curl, no PostgreSQL and no container socket. The health check is a static client of its own, precisely because there is nothing in the image to call an endpoint with, and debugging is done with a support bundle or the tools image rather than by installing something into a running container.

Versions between the parts

The agent protocol is versioned separately from the release, and this binary speaks version 1 with a minimum of 1. An agent of the previous release keeps working against a newer panel: every change of the protocol carries either compatibility with the release before it or a refusal that names what to upgrade (blocked_upgrade_required, protocol_incompatible). The order for an upgrade is therefore: the panel, then the relays, then the agents - and the agents are upgraded by the panel itself, separately, afterwards. A fleet running the previous agent against the new panel is an ordinary state, not a broken one.
